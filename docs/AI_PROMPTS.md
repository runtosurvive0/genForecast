# AI와 함께 개발할 때 복사할 지시

대괄호 부분을 실제 작업으로 바꾼다. Codex 등 자동으로 AGENTS.md를 읽는 도구도 있지만, 도구마다 지원 범위가 다르므로 아래처럼 직접 읽도록 지시한다. AI의 결과에 대한 책임은 PR 작성자에게 있다.

## 새 기능 시작

```text
이 저장소의 AGENTS.md, CONTRIBUTING.md, SPEC.md,
docs/DATA_DICTIONARY.md와 담당 폴더의 AGENTS.md를 먼저 읽어 줘.

git status와 remote를 확인하고 기존 변경을 보존해 줘.
깨끗한 상태라면 최신 main에서 아래 작업 브랜치를 만들어 진행해 줘.
이미 이 작업 브랜치라면 이어서 작업해 줘.

목표: [예: 저탄장 Pile 상세에 저장일수 기준 정렬 추가]
완료 조건: [예: 오름/내림 정렬, 선택한 Pile 유지, 모바일·양쪽 테마 정상]
브랜치: feature/stockyard-pile-sort
주 작업 폴더: src/features/stockyard/

상단바·사이드바와 공통 데이터 계약은 유지해 줘.
다른 화면을 직접 import하거나 계산 엔진을 복제하지 말아 줘.
범위 밖 공통 변경이 필요하면 이유와 영향을 먼저 설명해 줘.
작업에 필요한 테스트를 실행하고 실제 결과를 알려 줘.
완료 후 이번 작업 파일만 커밋하고 작업 브랜치로 push해 PR을 만들어 줘.
main 직접 push와 PR merge는 하지 말아 줘.
최종 보고에 변경 파일, 검증 결과, 미해결 사항, PR 링크를 남겨 줘.
```

발전소는 src/features/plant/와 feature/plant-..., 선박은 src/features/vessels/와 feature/vessels-...로 바꾼다. 목표·완료 조건은 하나의 PR에서 검토 가능한 크기로 적는다. 아직 원격에 올리기 싫으면 마지막 요청을 “로컬 수정·검증까지만 하고 commit/push/PR은 하지 마”로 바꾼다.

## 다른 팀원의 PR을 AI로 검토

```text
PR [번호 또는 URL]을 AGENTS.md와 SPEC 기준으로 검토해 줘.
내 작업 폴더의 변경을 보존하고 읽기 중심으로 검토해 줘.
코드 수정, 외부 댓글 등록, 승인, merge는 하지 말아 줘.
요구사항 누락, 계산·단위·시간 오류, 다른 화면 영향,
테스트 누락, 비밀키·실데이터 포함 여부를 확인해 줘.
발견한 문제마다 파일 위치, 영향, 재현 방법을 적어 줘.
실행한 검사와 실행하지 못한 검사를 구분해 줘.
문제 없다는 판단도 검토 범위와 한계를 밝혀 줘.
```

리뷰어 본인이 결과와 diff를 이해한 뒤 GitHub에서 Approve/Request changes를 선택한다. AI끼리 서로 “승인”한 것은 팀의 사람 리뷰 조건을 충족하지 않는다.

## main 변경 반영·충돌 해결

```text
현재 작업 브랜치에 최신 origin/main을 반영해 줘.
먼저 branch/status를 확인하고 미커밋 변경이 있으면 보존 방법부터 설명해 줘.
깨끗한 상태에서 fetch 후 merge origin/main을 사용해 줘.
충돌은 양쪽 변경의 목적을 비교해 해결하고 한쪽 전체 덮어쓰기는 하지 마.
공통 계약의 의미를 판단할 수 없으면 관련 차이와 확인할 내용을 알려 줘.
해결 후 단위 테스트·빌드·관련 UI 테스트를 실행해 줘.
force push, reset --hard, main 직접 push, PR merge는 하지 마.
```

## 머지 지시 — 사람 리뷰를 마친 뒤에만

```text
PR [번호]의 최신 변경에 대한 다른 팀원의 사람 승인,
CI verify 성공, UI 검증 결과, 충돌·미해결 리뷰 유무를 확인해 줘.
공통 파일 변경은 통합 담당자(작성자라면 다른 팀원)의 검토도 확인해 줘.
모두 충족하면 이 PR을 Squash merge해 줘.
조건이 부족하면 우회하거나 자동 merge를 예약하지 말고 부족한 항목을 알려 줘.
```

## 사람이 마지막에 읽을 항목

- AI가 요청한 기능과 관계없는 파일을 건드렸는가?
- 화면 표시값을 근거 없이 하드코딩하거나 테스트를 지웠는가?
- 실제로 실행한 테스트 결과인가? 빌드만 통과하고 UI 확인을 생략했는가?
- 더미 AIS·모의 위험도·합성 모델을 실시간 데이터처럼 설명하는가?
- 다른 팀원의 작업이나 공통 계약을 임의 변경했는가?
- 커밋에 키·사내 자료·생성 HTML이 들어갔는가?

이 목록은 형식적으로 체크하지 않고 PR의 실제 diff와 실행 결과로 확인한다.
