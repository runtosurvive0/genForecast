# 0단계: 시연용 더미 석탄·항차·부두 자료 설계

- 날짜: 2026-11-10
- 상태: 사용자 방향 승인(대화), 문서 검토 대기
- 후속: 1단계 화면별 도우미·빈 데이터 점검, 2단계 혼탄·저탄 추천, 3단계 접안 추천·간트·브리핑이 이 자료를 쓴다.

## 1. 목적

ZGX 공용 DB에는 실제로 입력된 기준재고(2026-11-08, 파일 32개)와 실제 항차 12건이 있다. 하지만 추천과 브리핑에 필요한 성상·부두·체선 자료는 거의 비어 있다. 이 단계에서는 빈 곳을 **더미 자료로 채운다.** 채운 값은 실제 값과 항상 구분해 표시하고, 언제든 지울 수 있게 한다.

사용자 요구(2026-11-09~10 대화):

- 실제 자료의 빈칸만 채운다. 이미 입력된 값은 바꾸지 않는다.
- 탄종 10개(AVRA, MERCURIA, Flame, Glencore, Glencore(무연탄), Centennial, KCH(Kaltim), KCH(adaro), KCH(Arutmin), LXI)를 공개 자료로 조사해 그럴듯한 성상을 만든다.
- 항차 범위는 26-1-001~26-1-041, 26-2-001~26-2-022, 26-3-001~26-3-038이다. ZGX에 있는 가장 큰 번호까지다.
- 성상은 황분만이 아니라 공업분석, 원소분석, 총수분, 회분, 회성분, 회융점, CSN 등 저장 칸 전체를 채운다.

## 3. 결정 사항

### 3.1 더미 표시: `data_origin`과 `dummy_fields`

- 항차·화물·성상 분석 표에 두 칸을 추가한다(공통 데이터 계약 변경, 통합 담당자 검토 필요).
  - `data_origin`: 선택값 `entered`(입력) / `dummy`(더미) / `mixed`(입력+더미). 기본값은 `entered`다. 마이그레이션 때 기존 행은 모두 `entered`로 둔다.
  - `dummy_fields`: 더미로 채운 칸 이름을 쉼표로 이은 문자열. `data_origin=dummy`인 행은 비워 두고, 모든 칸을 더미로 본다.
- 더미 항차의 `classification`은 `actual`로 둔다. 실제 운항 이력의 자리를 채우는 과거 항차이기 때문이다. 대신 `data_origin=dummy`로 더미를 표시한다. 기존 `simulation`(모의 시나리오) 분류와는 섞지 않는다.
- 사람이 원장 화면에서 더미 칸을 직접 고치면 그 칸을 `dummy_fields`에서 빼고, 남은 칸이 없으면 `data_origin=entered`로 바꾼다. 이 규칙은 원장 저장 함수 한 곳에서 처리한다.
- 화면: 원장 표와 성상 상세에서 더미 칸에 "더미" 표시를 붙인다. 행 단위 더미 항차에는 행 표시를 붙인다.
- 도우미 도구 결과: 항목마다 `data_origin`과 `dummy_fields`를 넘긴다. 시스템 지침에 "더미 값은 더미라고 밝힌다"를 넣는다. 이 부분의 구현은 1단계에서 한다. 0단계에서는 API 응답에 필드만 포함한다.

### 3.2 체선 조건 칸 추가

- 항차에 `laytime_hours`(허용정박시간, h)와 `demurrage_usd_per_day`(체선료, USD/일)를 추가한다(숫자, 선택값).

### 3.3 부두·저탄장 고정 자료

- 저장소에 `backend/src/midterm/dummy_data/berths.json`을 둔다.
  - BD-1~3마다 하역능력(t/h), 하루 작업 시간, 하역 불가 시간대 예시를 담는다.
  - 파일 머리에 `"classification": "dummy"`를 적는다.
- 3단계 접안 추천은 이 파일을 읽는다. 실제 부두 자료가 생기면 같은 형식의 실제 파일로 바꾼다.

### 3.4 탄종 성상 표(공개 일반값)

- 공개 자료 조사 결과를 `backend/src/midterm/dummy_data/coal_profiles.json`으로 커밋한다.
  - 탄종마다 원산지, 등급, 근거 수준("근거있음"/"추정"), 출처 주소를 적는다.
  - 항목별 대표값과 최소~최대 범위, 분석 기준을 담는다.
- 사내 자료, 계약값, 사진에서 옮긴 값은 쓰지 않는다. 범위는 공개 규격과 같은 원산지·등급의 일반값에서만 정한다.

### 3.5 생성기 `midterm.dummy_data.generate`

- 입력: 성상 표, 항차 번호 범위, 현재 ZGX 원장 스냅샷(이미 있는 행·값), 기준재고 파일 목록, 시드(기본 `20261110`).
- 출력: 원장 변경 목록(`voyage_registry.commit`에 그대로 넣는 형식)과 기준재고 보완본.
- 규칙:
  - 같은 입력과 같은 시드면 항상 같은 결과가 나온다. 항차번호와 탄종으로 하위 시드를 만든다.
  - 탄종 배정:
    - 이미 탄종이 정해진 실제 항차와 기준재고에 나온 항차는 그 탄종을 쓴다.
    - 나머지 항차는 부두별 실제 탄종 비율에 맞춰 시드로 고른다.
    - 무연탄 Glencore(무연탄)는 5% 이하로 둔다.
  - 일정: 2026-01-01부터 항차번호 순서대로 부두별로 배치한다. 같은 부두 안에서 번호가 작을수록 앞선다.
    - 일정이 입력된 실제 항차가 있으면 그 날짜 사이에 끼워 넣는다.
    - 각 부두의 가장 큰 번호(26-1-041, 26-2-022, 26-3-038)는 실제 항차이므로, 더미 항차는 모두 그보다 앞선 과거 항차가 된다. 진행상태는 하역 완료다.
    - 앞으로 입항할 계획 선박은 이 단계에서 만들지 않는다. 범위를 넘는 번호가 필요하기 때문이며, 3단계에서 따로 정한다.
  - 물량: 탄종별 일반 선형(Panamax 60~85kt, Capesize 120~170kt)에 맞추고, B/L 대비 입고량 오차는 ±0.5% 이내로 둔다.
  - 성상: 화물마다 선적(loading)과 하역(unloading) 분석을 2건 만든다.
    - `result_status=confirmed`, 분석기관은 `더미(공개 일반값)`로 적는다.
    - 하역 분석은 선적 분석에서 수분 +0~1.5%p, 발열량 그에 맞춰 낮춤을 반영한다.
  - 일관성(생성 직후 검사, 어기면 생성 실패):
    - 공업분석 ADB IM+VM+Ash+FC = 100±0.1
    - 원소분석 DB C+H+N+O+S + Ash(DB) = 100±0.5
    - GCV ARB < ADB < DB, NCV < GCV ARB
    - S_AR = S_DB × (100−TM)/100 ± 0.01, `sulfur_pct`(AR)와 `s_db`가 일치
    - 회성분 합계 = 100±0.5, 회융점 IT ≤ ST ≤ HT ≤ FT
    - 모든 값이 저장 칸의 min~max 안에 있음
  - 화물 표의 대표 성상(cv, cv_basis=GAR, moisture_pct, ash_pct, sulfur_pct, analysis_basis=AR)은 하역 분석값으로 채운다.
  - 체선: 허용정박시간 72~120h, 체선료는 선형별 15,000~35,000 USD/일로 둔다.
  - 기준재고 보완:
    - 비어 있는 `age_days`는 연결 항차의 하역 완료일부터 기준일까지 일수로 채운다.
    - `temperature_c`는 적치일수·고/저열에 따라 25~60°C로 만든다. 저열·장기 적치일수록 높게 한다.
    - 기준재고 저장 허용 칸에 `temperature_c`와 `dummy_fields`를 추가한다.

### 3.6 적재기 `python -m midterm.dummy_data load|unload|check`

- `check`: 대상 DB를 읽기만 하고, 넣을 행 수·채울 칸 수·건드리지 않을 실제 값 수를 출력한다.
- `load`:
  1. SQLite backup API로 `~/.config/genforecast/backups/dummy-<시각>/`에 백업한다.
  2. 생성기 결과를 `voyage_registry.commit(changes, revision, actor='dummy-seed', origin='dummy-data')`로 한 번에 넣는다.
     - 원장 이력에 남고, revision 충돌을 검사한다.
     - 빈칸만 채운다. 값이 있는 칸은 건너뛰고 건너뛴 수를 출력한다.
  3. 기준재고 보완본을 같은 as_of의 새 revision으로 저장한다(actor `dummy-seed`).
  4. 다시 실행해도 결과가 같다. 이미 더미가 들어간 행은 같은 값으로 판정해 바꾸지 않는다.
- `unload`:
  - 원장 이력에서 `origin='dummy-data'`인 변경을 찾는다.
  - 더미로 만든 행은 지우고, 실제 행에 채운 칸은 비운다. 이때 이후 사람이 고친 칸은 건드리지 않는다.
  - 기준재고는 더미 직전 revision으로 되돌린 새 revision을 만든다.
- 실행 위치: 저장소 코드다. ZGX에서는 사용자가 다음 명령으로 직접 실행한다.

  ```bash
  /home/puyo/genforecast/current/.venv/bin/python -m midterm.dummy_data <명령>
  ```

  - 대상 DB는 `MIDTERM_PLANNING_DB`를 따른다.
  - Claude는 ZGX에 쓰지 않는다.

## 5. 시험

- 생성기(백엔드 pytest):
  - 같은 시드면 같은 결과
  - 3.5의 일관성 검사 전부
  - 항차 범위 101건 생성(기존 12건 + 새 89건)
  - 실제 값 보존, 탄종 배정 규칙
- 적재기(임시 DB, 고정 자료):
  - load 후 빈칸만 채워짐, 실제 값 그대로
  - 두 번 load해도 변화 없음
  - load 후 사람이 칸 하나를 고친 뒤 unload하면 그 칸은 남음
  - unload 후 원래 스냅샷과 같음(더미 행·칸 없음)
  - 백업 파일 생성
- 원장 계약:
  - 마이그레이션으로 기존 행이 `data_origin=entered`가 됨
  - 사람이 더미 칸을 고치면 `dummy_fields`에서 빠짐
- 화면(Playwright): 원장 표에 더미 표시가 보이고 라이트·다크, 390px에서 깨지지 않음
- 공통: `npm test`, `npm run build`, `npm run test:ui`, 백엔드 전체(highspy 3건 제외 실패 없음)

## 6. 위험과 대응

- 더미가 실제 값으로 오인될 수 있다. 행·칸·도구 결과 모두에 표시하고, `unload`로 언제든 걷어낼 수 있게 한다.
- 공용 DB에 대량으로 쓴다. 백업 후 실행하고, `check`로 미리 보고, 원장 이력에 남긴다. 실행은 사람이 한다.
- 공개 자료가 부족한 탄종이 있다. "추정"으로 표시하고 같은 원산지 일반값을 쓴다. 출처를 성상 표에 남긴다.
- 원장 구조가 바뀐다. 칸 추가만 하므로 이전 코드와 호환되고, 자동 갱신의 되돌리기와도 충돌하지 않는다(docs/ZGX_AUTO_DEPLOY.md의 호환 규칙).
