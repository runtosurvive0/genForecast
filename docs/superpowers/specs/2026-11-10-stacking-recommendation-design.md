# 운영 도우미 2단계: 하역 대기 화물 적치 추천 설계

- 날짜: 2026-11-10 (KST)
- 앞 단계: 0단계 더미 자료(PR #24), 1단계 화면별 도우미 섹션·빠진 자료 점검(PR #25, ZGX 배포 완료)
- 후속: 3단계 접안 추천·간트·AI 브리핑. 3단계의 시간축 배정은 이 문서의 추천 함수를 시각마다 반복 호출하는 방식으로 확장한다.
- 근거 문서: `docs/GEN4CAST_SCREEN_ROADMAP.md` 15행 "배치 추천"

## 1. 목적

배가 들어와 있거나 곧 들어오는데 아직 하역을 시작하지 않았을 때, 그 배의 화물(탄종·열량·물량)을 저탄장 어디에 내리면 되는지 후보를 근거와 함께 보여 준다. 화면과 운영 도우미가 같은 계산으로 같은 답을 낸다.

추천은 제안이다. 재고·원장·기준재고를 바꾸지 않는다. 채택과 저장은 사람이 기존 화면에서 한다.

## 2. 정한 것 (사용자 확인)

| 항목 | 결정 |
|---|---|
| 범위 | 적치 추천을 새로 만든다. 이미 있는 혼탄 추천(`blend_recommendation.py`)은 도우미 도구로 연결만 한다 |
| 입력 | 공통 화물 형식. 시나리오 선박을 먼저 붙이고, 항차 원장 항차도 같은 형식으로 바꿔 넣는다. 원장 자료는 바꾸지 않는다 |
| 실제 AIS 선박 | 합성 화물을 붙이지 않는다. 원장과 MMSI/IMO로 연결될 때만 추천을 보여 준다 |
| 적치 규정 | 다른 항차의 탄은 같은 자리에 쌓지 않는다. 빈 구간·빈 칸에만 추천한다 |
| 필수 조건 | 반입 경로, 남은 공간, 고/저열량 분리 |
| 점수 조건 | 오래 쌓였거나 온도가 높은 원탄 바로 옆 구간을 피한다 |
| Pile 용량 | 편집 가능한 모의 설정 파일. 실제 값이 생기면 같은 형식으로 바꾼다 |
| 구조 | 백엔드 추천 모듈 하나를 화면 API와 도우미 도구가 같이 쓴다 |
| 저탄장 화면 | 추천 구간 강조를 이번 범위에 넣는다 |

## 3. 입력: 공통 화물 형식 `CargoRequest`

| 필드 | 형식 | 설명 |
|---|---|---|
| `source` | `"scenario"` \| `"registry"` | 출처. 결과에 그대로 돌려준다 |
| `ref` | 문자열 | 시나리오 선박 id 또는 `voyage_no` |
| `vessel_name` | 문자열 | 선명 |
| `voyage_number` | 문자열 \| null | 항차 번호. 같은 항차 판정에 쓴다 |
| `coal_name` | 문자열 \| null | 탄종 |
| `grade` | `"고"` \| `"저"` \| null | 고/저열량. 기준재고의 `grade`와 같은 분류 |
| `cv` | 숫자 \| null | kcal/kg |
| `tonnes` | 숫자 | 0 초과 1,000,000 이하 |
| `berth` | 1 \| 2 \| 3 | 하역 부두 |
| `destination_yard` | 1 \| 2 \| 3 \| null | 목적 저탄장 |

- 시나리오 선박: 프런트가 `src/data/demo-forecast-sample.ts`의 값(grade `low/high` → `저/고`, `yard` `Y1~3` → 1~3, `cargo − unloaded` → tonnes)을 바꿔 보낸다.
- 원장 항차: 백엔드가 `voyage_no`로 `voyage_registry_cargo`를 읽어 만든다.
  - 당진행(`destination_plant_id = dangjin`) 화물만 합산한다.
  - 같은 항차에 탄종이나 고/저 구분이 다른 화물이 섞여 있으면 추천하지 않고 "한 항차 여러 탄종"을 돌려준다.
  - 부두는 `berth_id`(`BD-1~3`)에서 읽는다. 없으면 추천하지 않고 "부두 미배정"을 돌려준다.
  - 고/저 구분은 탄종 분류를 따른다. 기준재고에 같은 탄종(`coal_name`) 원탄이 있으면 그 `grade`를, 없으면 0단계 탄종 프로필(`dummy_data/profiles.py`의 `class`: `high_cv`/`low_cv`)을 쓴다. 둘 다 없으면 null이다. `cv`로 새 경계를 만들지 않는다.

## 4. 저탄장 빈 곳 계산

기준은 현재 기준재고(`yard_baselines` 최신 revision)다. 기준시각 `as_of`를 결과에 붙인다.

### 4.1 Pile 1~8 (1·2저탄장)

- Pile 하나를 0 m부터 `length_m`까지의 선분으로 본다. 원탄마다 `[start_m, end_m]` 구간을 차지한다.
- 빈 구간 = 선분에서 원탄 구간을 모두 뺀 나머지. 겹치는 구간은 합쳐서 뺀다. 길이 `min_gap_m` 미만은 버린다.
- 빈 구간에 들어갈 물량 = 빈 구간 길이 × 그 Pile의 m당 톤수.
  - m당 톤수 = 같은 Pile 원탄의 `tonnes` 합 ÷ 구간 길이 합(구간이 있는 원탄만).
  - 그런 원탄이 없으면 설정 파일의 `default_t_per_m`을 쓰고 "모의 m당 톤수"로 표시한다.
- 구간을 모르는 원탄(`start_m`/`end_m`이 없고 기존 참고 위치도 없는 원탄)이 하나라도 있는 Pile은 빈 곳을 확정할 수 없다. 후보에서 빼고 "구간 미확인: Pile n"으로 보고한다.

### 4.2 3저탄장 Shed A/B

- 칸 1~10 단위. 원탄이 없는 칸이 빈 칸이다.
- 칸당 용량은 설정 파일의 `shed_cell_t`(모의)를 쓴다.
- 인접 칸은 같은 Shed에서 번호가 1 차이 나는 칸이다.

### 4.3 설정 파일 `stacking_layout.json` (모의)

- 위치: `backend/src/midterm/stacking_layout.json`, 프런트 사본 `src/data/fuel-reference/stacking-layout.json`. 두 파일이 같은지 시험으로 확인한다(부두 좌표 파일과 같은 방식).
- 내용: Pile 1~8의 `length_m`, `default_t_per_m`, `min_gap_m`, `shed_cell_t`, 인접 위험 기준(`old_age_days`, `hot_temperature_c`), 그리고 `classification: "모의"` 표시.
- Pile 길이 초기값은 기존 장면 자료(`yard-snapshot.js`, `yard2-calibration.js`, `berth-site-layout.js`)의 길이를 따른다. 모르는 값은 모의 값으로 두고 파일에 출처를 적는다.

### 4.4 반입 경로

- `src/data/fuel-reference/demo-catalog.json`의 `routes`(부두 → `pile-n` / `shed-a` / `shed-b`)를 백엔드가 같은 파일에서 읽는다. 모의 설비다.

## 5. 후보 선택

### 5.1 필수 조건 (하나라도 어기면 제외)

1. 그 부두에서 반입 경로가 있는 Pile/Shed다.
2. 빈 구간 또는 빈 칸이다. 다른 항차 탄이 있는 구간·칸은 쓰지 않는다.
3. 고/저열량이 섞이지 않는다. Pile(또는 Shed)에 이미 다른 등급 원탄이 있으면 제외한다. 화물 `grade`가 null이면 이 조건을 확인할 수 없으므로 추천하지 않고 "고/저 구분 미확인"을 돌려준다.

### 5.2 배치안 만들기

- 한 곳(빈 구간 하나 또는 빈 칸 하나)에 다 들어가는 안을 먼저 만든다.
- 한 곳에 안 들어가면 같은 저탄장 안의 두 곳으로 나누는 안을 만든다. 세 곳 이상은 만들지 않는다.
- 빈 구간에는 앞쪽(작은 m)부터 화물 길이만큼만 차지하는 구간을 제안한다(`tonnes ÷ t_per_m`, 0.5 m 단위 올림).

### 5.3 점수 (높은 순 정렬, 앞 기준이 우선)

1. 목적 저탄장과 일치(목적 저탄장이 없으면 모두 같음)
2. 나눠 내리는 곳 수가 적음
3. 제안 구간 바로 옆(같은 Pile에서 맞닿거나 `min_gap_m` 안, Shed는 인접 칸)에 `age_days ≥ old_age_days` 또는 `temperature_c ≥ hot_temperature_c`인 원탄이 없음
4. 빈 구간 낭비가 적음(빈 구간 용량 − 화물 물량이 작을수록 좋음)

### 5.4 결과 형식

```json
{
  "as_of": "기준재고 기준시각",
  "cargo": { "...": "받은 CargoRequest" },
  "options": [
    {
      "rank": 1,
      "placements": [{ "yard": 1, "target": "Pile 3", "from_m": 130.0, "to_m": 210.5, "tonnes": 75000 }],
      "reasons": ["1저탄장(목적지)", "한 곳에 모두 적치", "옆 구간에 오래된 원탄 없음"],
      "warnings": ["옆 구간 LXI 원탄 적치 32일"],
      "assumptions": ["Pile 길이 모의 값", "반입 경로 모의 설비"]
    }
  ],
  "no_fit": null,
  "gaps": ["구간 미확인: Pile 6"]
}
```

- `options`는 최대 3개다.
- 들어갈 곳이 없으면 `options`는 빈 목록이다. `no_fit`에 "들어갈 빈 곳 없음"과 가장 큰 빈 구간(위치·추정 물량)을 담는다.
- 모든 숫자는 계산 결과에서만 나온다.

## 6. 하역 대기 항차 찾기 (원장)

`GET /api/stacking/candidates`와 도구 `stacking_candidates`가 같은 함수를 쓴다. 조건:

- `status = arrived`, `berth_id`가 있음, `actual_unload_end`가 없음
- 당진행 화물이 있음
- 기준재고에 아직 들어가 있지 않음: 기준재고 원탄의 `voyage_number`에 그 항차 번호가 없음

0단계 더미 항차 중 도착 상태 11건은 이미 기준재고에 들어가 있어 대상에서 빠진다. 이미 쌓인 화물에 다시 추천하지 않기 위해서다.

## 7. API

| 경로 | 권한 | 동작 |
|---|---|---|
| `POST /api/stacking/recommend` | 로그인·승인 사용자 | `CargoRequest`(또는 `{ "voyage_no": ... }`)를 받아 5.4 결과를 돌려준다. 저장하지 않는다 |
| `GET /api/stacking/candidates` | 로그인·승인 사용자 | 6절 목록을 `CargoRequest` 형식으로 돌려준다 |

- `POST /api/stacking/recommend`는 `auth_api.READ_POST`에 넣는다. CSRF 검사는 그대로 둔다.
- 두 경로 모두 사용자별 분당 60회로 제한한다(1단계 `/api/assistant/checks`와 같은 방식).
- 입력 오류는 422, 알 수 없는 오류는 "내부 오류(서버 로그 확인)"로 응답한다.

## 8. 화면

### 8.1 발전소 전망(시나리오) → 선박 목록 (`src/features/forecast/DemoForecast.tsx`)

- 상태가 체선·근거리이거나, 접안했지만 하역량이 0인 배의 행에 "적치 추천" 버튼을 둔다. 하역 중이거나 완료된 배에는 두지 않는다.
- 누르면 행 아래에 펼친다: 추천안(Pile·구간 m·예상 물량), 근거, 경고, 빠진 자료·모의 값.
- 문구: "시나리오 가정 · 현재 기준재고 기준". 멀리 있는 배는 도착할 때 재고가 달라질 수 있음을 함께 적는다.
- 펼친 상태에서 도우미를 열면 그 배를 맥락으로 넘긴다.

### 8.2 부두 화면 (`src/features/berth/OperationsBerth.tsx`)

- AIS로 관측한 배가 원장과 연결되고(`matchCargo`) 하역 대기 항차가 있을 때만, 화물 아래에 1순위 추천을 한 줄로 보여 준다.
- 연결되지 않으면 아무것도 표시하지 않는다. 지금 접안한 실제 선박에는 합성 화물을 붙이지 않는다.

### 8.3 저탄장 화면 (`src/features/stockyard/OperationsYard.tsx`)

- 추천안에서 "저탄장에서 보기"를 누르면 저탄장 화면으로 이동해 해당 Pile의 제안 구간을 강조한다.
- 강조는 기존 Pile 막대(`gf-oy-stock-strip`)와 장면 위에 표시만 한다. 재고 표시는 바꾸지 않는다.
- 화면끼리 직접 import하지 않는다. 추천 결과 형식과 이동 값은 `src/domain/`에 두고 `App.tsx`가 연결한다.

### 8.4 공통

- 추천 결과 타입과 API 호출은 `src/domain/stacking.ts`에 둔다. 표시 부품이 여러 화면에서 필요하면 `src/components/`에 둔다.
- 모의 값을 썼다는 사실은 각 추천안의 `assumptions`로 보여 준다. 화면 위쪽 공통 모드 표시 규칙은 그대로 둔다.
- 라이트/다크, 390px 폭에서 가로 넘침이 없어야 한다.

## 9. 운영 도우미

| 도구 | 인자 | 동작 |
|---|---|---|
| `recommend_stacking` | `CargoRequest` 필드 또는 `voyage_no` | 5절 계산. 결과 봉투의 `source`는 `scenario`/`registry`, `as_of`는 기준재고 기준시각 |
| `stacking_candidates` | 없음 | 6절 목록 |
| `recommend_blend` | 요청량·목표 발열량·허용오차·상한(기존 함수 인자) | 기준재고 원탄으로 기존 `recommend_blend` 호출. 저장하지 않는다 |

- 도우미 답의 숫자는 기존 facts 대조를 그대로 거친다.
- `AskRequest.context`의 허용 키에 `vessel`(시나리오 선박 id 또는 `voyage_no`)을 추가한다.
- 시나리오 화면 도우미 섹션 예시 질문: "체선 중인 배 화물은 어디에 내리면 돼?", "GEN4CAST OCEAN 적치 추천해 줘".
- 1단계 점검(`run_checks`)에 항목을 추가한다: `stacking.mock_layout`(모의 Pile 길이·칸 용량 사용, kind `dummy`), `stacking.unplaced`(구간 미확인 원탄, kind `missing`).

## 10. 오류와 빈 자료

| 상황 | 동작 |
|---|---|
| 기준재고 없음·읽기 실패 | 추천하지 않음. "기준재고 없음". 합성 값으로 대신하지 않는다 |
| 화물 고/저 구분 없음 | 추천하지 않음. "고/저 구분 미확인" |
| 화물 열량만 없음 | 추천하되 "열량 미확인" 경고 |
| 한 항차 여러 탄종 | 추천하지 않음. "한 항차 여러 탄종" |
| 부두 미배정 | 추천하지 않음. "부두 미배정" |
| 입력 범위 오류 | 422. 도구는 실패로 돌려주고 gaps에 적는다 |
| 설정·경로 파일 오류 | 서버 로그, "내부 오류(서버 로그 확인)" |

## 11. 검증

- **계산 단위 시험** (pytest, 격리 자료): 빈 구간(양끝·중간·겹침·최소 길이 미만), 구간 미확인 Pile 제외, 다른 항차 구간 제외, 고/저 혼합 금지, 반입 경로 없는 Pile 제외, 두 곳 나누기, 들어갈 곳 없음과 최대 빈 구간, 옆 구간 오래됨·고온 시 순위 하락, Shed 빈 칸과 인접 칸, 모의 m당 톤수 표시, 목적 저탄장 우선.
- **원장 변환 시험**: 화물 여러 건 합산, 탄종 혼재 거부, 부두 미배정, 이미 기준재고에 들어간 항차 제외.
- **API 시험**: 로그인·승인 필요, CSRF, 요청 수 제한, 422, 저장 함수가 호출되지 않음.
- **사본 일치 시험**: `stacking_layout.json` 두 사본.
- **도우미 시험**: 가짜 LLM으로 세 도구 호출과 facts 대조. 평가 질문셋(`backend/tests/assistant_eval/questions.jsonl`)에 적치 문항 추가.
- **Playwright** (API 모킹): 시나리오 선박 행 추천 펼침, 하역 중인 배에는 버튼 없음, 부두 화면 한 줄 추천(연결 시만), 저탄장 구간 강조, 들어갈 곳 없음, 기준재고 없음, 390px, 다크 모드.
- **전체**: `npm test`, `npm run build`, `npm run test:ui`, 백엔드 pytest, `git diff --check`.

## 12. 범위 밖

- 시간에 따라 앞으로 올 배들의 Pile을 순서대로 배정(3단계)

- 실제 Pile 측량값·실제 설비 경로
- 혼탄 추천 계산 자체의 변경

## 13. 공통 영향
