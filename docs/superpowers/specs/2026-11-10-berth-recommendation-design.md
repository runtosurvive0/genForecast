# 운영 도우미 3단계: 접안 추천(여러 안 비교) 설계

- 작성일: 2026-11-10 (KST)
- 상태: 사용자 검토 대기
- 근거 문서: `2026-11-09-llm-ops-assistant-design.md` 5절(체선료 최소 접안 일정), 8절 3단계. 이 문서는 그 5절을 그대로 따르고, 여러 안 비교와 화면을 정한다.
- 선행: 2단계 적치 추천(PR runtosurvive0/genForecast#31), 더미 계획 항차(#33·#36), 수급 원장 계획 입하(#33·#35).
- 후속: 혼탄 추천 화면은 별도 설계 문서로 한다.

## 1. 목적

입항 예정·대기 중인 배를 어느 부두에 언제 대야 하는지 **여러 안을 함께** 추천한다. 안마다 체선료와 저탄장 재고일수에 미치는 영향을 현재 계획과 나란히 보여 주어, 담당자가 고른다. 화면과 운영 도우미가 같은 계산으로 같은 답을 낸다.

## 2. 정한 것 (사용자 확인)

| 항목 | 결정 |
|---|---|
| 순서 | 접안 추천을 먼저 설계한다. 혼탄 추천은 다음 문서 |
| 계산 | 근거 문서 5.1의 MILP(HiGHS, 1시간 슬롯)를 그대로 쓴다 |
| 목표 | 체선료와 재고 위험을 점수 하나로 합친다(2026-11-10). 가중치만 바꾼 안 여러 개를 함께 보인다 |
| 반영 | 읽기 전용 제안. 원장에 저장하지 않는다(근거 문서 1절 4번) |
| 결과 표시 | 접안 간트 + "기존 일정 대비" 표(근거 문서 4.3) |

## 3. 대상과 입력

### 3.1 대상 항차

- 항차 원장(`voyage_registry`)에서 목적발전소 당진 화물이 있고, `classification`이 `simulation`이 아닌 항차.
- **배정 대상**: 상태 `planned`·`underway`·`arrived`이고 `planned_arrival`이 기준시각부터 기간(기본 14일) 안인 항차.
- **고정 점유**: 상태 `berthed`·`unloading`인 항차는 `berth_id`에서 지금부터 `planned_unload_end`까지 부두를 차지하는 것으로 고정한다. 이 값이 없으면 그 부두는 "점유 끝 미확인"으로 기간 끝까지 막고 `gaps`에 적는다.
- 화물량은 항차의 당진 화물 `bl_t`(없으면 `planned_t`) 합계. 0 이하이면 대상에서 빼고 `gaps`에 적는다.
- ETA는 `planned_arrival`. 없으면 대상에서 빼고 `gaps`에 적는다.

### 3.2 부두 자료

- `backend/src/midterm/dummy_data/berths.json`을 읽는다(분류 `dummy`, 시연용 가정값).
  - `unload_tph`, `work_hours_per_day`, `max_dwt`, `yards`, `outage_examples`.
- 하역 시간 = `ceil(화물량 / unload_tph / work_hours_per_day × 24)` 시간. 근거 문서의 `ceil(화물량 / 부두 하역능력)`에 작업시간 비율을 더한 것으로, 더미 생성기(`generate.py`)와 같은 식이다.
- 부두가 저탄장으로 보낼 수 있는지: 항차 `yard`가 그 부두 `yards`에 있어야 한다. `yard`가 비어 있으면 모든 부두를 허용하고, "저탄장 미배정"을 `gaps`에 적는다.
- **선형 제한**: 선박 원장에 DWT·LOA 칸이 없다. 이번에는 선형 제한을 적용하지 않고, 결과에 "선형 제한 미적용(선박 제원 없음)"을 `gaps`로 한 번 적는다. 제원을 지어내지 않는다.
- 정비(`outage_examples`): 그 시간대에는 하역을 시작하지 않는다. 하역 중에 정비가 끼면 그 길이만큼 하역 완료가 늦어진다.

### 3.3 체선료

- 항차 `laytime_hours`, `demurrage_usd_per_day`. 체선 시간 = max(0, 하역 시작 − ETA − 허용정박시간).
- 둘 중 하나라도 없으면 그 항차는 체선료 목적에서 빼고(배정은 한다) `gaps`에 적는다. 기본값을 추정해 넣지 않는다.
- 기산 기준(`laytime_start_rule`)은 원장에 아직 없다. 이번에는 ETA 기산으로 계산하고 결과에 "ETA 기산 가정"을 적는다.

### 3.4 재고

- 수급 원장(`supply.py`의 현재 결과)을 쓴다. 저탄장 그룹(g14·g58·g910)별 일 사용량, 기준재고, 계획 입하.
- 계획 입하 중 이번 배정 대상 항차의 입하는 빼고, 배정 결과의 하역완료 시각에 다시 넣는다. 나머지 입하는 그대로 둔다.
- 재고일수 = 재고 ÷ 다음 7일 계획 사용 평균(수급 원장과 같은 식). 분모는 날짜별 상수라 입하 시점에 대해 선형이다.
- 기준재고가 없거나 오래돼(`baseline_stale_hours` 초과) 재고를 모르면 재고 제약·벌점을 끄고, 체선료만으로 한 안만 보인다. 이유를 `gaps`에 적는다.

## 4. 계산

### 4.1 공통 제약 (근거 문서 5.1)

1. 각 항차는 한 번만 접안한다.
2. 부두마다 한 번에 한 척만 하역한다.
3. ETA 전에 접안하지 않는다.
4. 부두에서 그 저탄장으로 보낼 수 있어야 한다(3.2).
5. 정비 시간에는 하역을 시작하지 않는다(3.2).
6. 그룹별 재고일수 ≥ `danger_days`(기본 7일). 이 제약 때문에 풀 수 없으면 6번을 벌점으로 바꿔 다시 풀고, "위험 기준을 지킬 수 없음"을 그 안의 경고로 보인다.
7. `locks[]`: 도우미나 API 호출에서 고정한 항차·부두·시각. 화면에는 고정 기능을 이번에 넣지 않는다.

### 4.2 세 안

같은 제약에서 목적만 바꿔 세 번 푼다.

| 안 | 목적 | 비고 |
|---|---|---|
| A. 체선 최소 | Σ 체선료 | 근거 문서의 기본안 |
| B. 균형 | Σ 체선료 + 벌점 단가 × Σ(그룹·일, 재고일수 < `normal_days`) | 기본 추천 |
| C. 재고 우선 | Σ 체선료 + 10 × 벌점 단가 × Σ(같은 항) | 체선료를 더 내더라도 주의 구간을 먼저 없앤다 |

- **벌점 단가**: 주의 구간 그룹·일 1개당 USD. 기본 20,000 USD(시연용 가정값, 더미 체선료 일 단가와 같은 크기). API 인자로 바꿀 수 있고, 화면에 "가정값"으로 보인다.
- 주의 구간 판정은 일 단위(자정 기준)로 한다.
- 결과 배정이 같은 안은 하나로 합치고 "A·B 같음"처럼 적는다.
- 더미 항차는 허용정박이 72~120시간이라 체선이 거의 없을 수 있다. 그러면 세 안이 하나로 합쳐질 수 있고, 그것도 정상 결과로 "세 안 같음 · 체선·재고 차이 없음"을 보인다.
- **추천 순위**: B를 1순위로 표시한다. B와 다른 안이 같으면 합친 안을 1순위로 한다.
- 풀이 제한은 안마다 30초. 시간 안에 최적을 못 찾으면 그때까지의 최선해와 차이(gap %)를 보인다. 해가 하나도 없으면 그 안은 "해 없음"과 이유를 보인다.

### 4.3 현재 계획 (비교 기준)

- 원장의 `berth_id`·`planned_berth`·`planned_unload_end`를 그대로 쓴 일정을 같은 식으로 평가한다(풀지 않는다).
- 부두나 접안 예정 시각이 비어 있는 항차는 현재 계획에서 "미배정"으로 두고, 체선·재고 평가에서 그 화물의 입하는 `planned_unload_end`(없으면 제외)로 둔다.

### 4.4 걸린 제약 설명

체선이 생긴 항차마다 원인을 하나 이상 붙인다.

- `berth_busy`: ETA부터 하역 시작까지 갈 수 있는 부두가 모두 다른 배로 차 있었다.
- `outage`: 정비 시간 때문에 시작을 미뤘다.
- `stock_priority`: 다른 저탄장의 재고 하한·벌점 때문에 다른 배가 먼저 들어갔다(그 배 항차번호를 함께 적는다).

원인은 결과 일정에서 사후 판정한다(MILP 쌍대값을 쓰지 않는다).

## 5. 결과 형식

```json
{
  "as_of": "2026-11-10T09:00:00+09:00",
  "horizon_days": 14,
  "source": {"berths": "dummy", "voyages": "registry", "stock": "supply_ledger"},
  "assumptions": ["부두 능력: 시연용 가정값", "ETA 기산 가정", "벌점 단가 20,000 USD/그룹·일(가정값)"],
  "gaps": [{"kind": "no_demurrage", "voyage_no": "...", "message": "체선료 값 없음 · 체선료 계산에서 제외"}],
  "current": {"label": "현재 계획", "kpis": {...}, "assignments": [...]},
  "options": [
    {"id": "B", "rank": 1, "label": "균형", "merged": ["B"], "status": "optimal", "gap_pct": 0,
     "kpis": {"demurrage_hours": 0, "demurrage_usd": 0, "min_days": 0, "caution_days": 0, "danger_days": 0,
              "demurrage_usd_delta": 0},
     "warnings": [],
     "assignments": [{"voyage_no": "...", "voyage_number": "...", "vessel_name": "...", "yard": "2",
                      "berth_id": "BD-1", "eta": "...", "berth_at": "...", "unload_end": "...",
                      "tonnes": 0, "demurrage_hours": 0, "demurrage_usd": 0, "reasons": ["berth_busy"],
                      "changed": true}]}
  ]
}
```

- `kpis.min_days`는 기간 중 그룹별 최저 재고일수의 최솟값. 재고를 모르면 `null`.
- `changed`는 현재 계획과 부두나 접안 시각(1시간 이상 차이)이 다른지.
- 고정 점유 항차는 `assignments`에 `fixed: true`로 넣어 간트에 함께 그린다.

## 6. API와 도구

| 경로 | 권한 | 설명 |
|---|---|---|
| `POST /api/berth-plan/recommend` | 로그인·승인 사용자 | 본문 `{horizon_days?, penalty_usd?, locks?}`. 5절 결과를 돌려준다. 저장하지 않는다 |

- 위치: `backend/src/midterm/berth_plan/`(`inputs.py` 입력 모으기, `solve.py` MILP, `explain.py` 원인 판정). API는 `web/berth_plan_api.py`로 두고 `web/stacking_api.py`와 같은 라우터 방식을 따른다.
- 입력 오류(기간 1~30일 밖, 음수 벌점, 잘못된 lock)는 422.
- 운영 도우미 도구 `optimize_berth_schedule`: 같은 함수를 부른다. 답은 1순위 안을 중심으로 하고, 다른 안의 차이와 `gaps`를 함께 말한다. 숫자는 결과에서만 쓴다.
- HiGHS는 기존 `highs_backend.py` 의존성(`highspy`)을 쓴다. 새 의존성은 없다.

## 7. 화면

### 7.1 위치

- 통합 시뮬레이션 화면 상단 탭에 "접안 추천"을 둔다. 기존 탭: 저장된 발전·수급 계획 / 단기 조건 비교 / 구매 검토 / 계산 입력·실행.
- 폴더: `src/features/berth-plan/`. 결과 타입과 API 호출은 `src/domain/berth-plan.ts`. `App.tsx`가 연결한다.
- 수급 예측 화면의 가상 접안 간트는 바꾸지 않는다.

### 7.2 구성

1. **조회 막대**: 기준시각(KST), 기간(7·14·30일, 기본 14), 벌점 단가(가정값, 숫자 입력), "다시 계산" 버튼. 계산 중에는 `ProcessingOrb`(solving).
2. **안 카드**: 현재 계획 1개 + 안 최대 3개를 한 줄로 둔다.
   - 카드마다: 이름, 추천 표시(1순위), 체선 시간·체선료, 최저 재고일수, 주의·위험 일수, 현재 대비 체선료 차이.
   - 카드를 누르면 아래 간트와 표가 그 안으로 바뀐다. 기본 선택은 1순위 안.
3. **간트**: 부두 3줄 × 기간. 선택한 안의 하역 막대(저탄장별 색), 현재 계획 막대는 흐린 테두리로 겹친다. 정비 시간은 빗금. ETA는 막대 앞의 점, 체선 구간은 막대 앞 줄무늬. 고정 점유 항차는 회색.
4. **항차 표**: 항차번호·선박·저탄장·물량·ETA·부두·접안·하역완료·체선(시간·USD)·원인·변경. 행의 "적치 추천"으로 기존 적치 추천을 연다(2단계 부품 `StackingOptions` 재사용).
5. **가정·빠진 자료**: 표 아래 접힘 칸에 `assumptions`와 `gaps`.

- 모의·가정 표시는 공통 규칙대로 한다. 부두 능력이 더미이므로 조회 막대 옆에 "부두 능력 시연용 가정값" 한 줄을 둔다.
- 라이트/다크, 1920×1080에서 카드·간트가 한 화면, 390px 폭에서 가로 넘침 없음(간트는 가로 스크롤 영역 안).

## 8. 오류와 빈 자료

| 경우 | 처리 |
|---|---|
| 대상 항차 0척 | "기간 안 입항 예정 선박 없음". 안을 만들지 않는다 |
| 원장·수급 원장 읽기 실패 | 오류를 보인다. 합성 값으로 대신하지 않는다 |
| 재고 모름 | 재고 제약·벌점 끄고 A안만. 이유를 `gaps`에 |
| 위험 기준 불가 | 6번 제약을 벌점으로 바꿔 풀고 경고 |
| 풀이 시간 초과 | 최선해와 gap % |
| 해 없음 | 그 안에 "해 없음"과 이유 |
| 체선료·허용정박 없음 | 체선료 계산 제외, 배정은 함 |

## 9. 검증

- **pytest(격리 DB)**
  - 손으로 풀 수 있는 3척·2부두 예제: 최적 배정과 체선료가 기대값과 같다.
  - 재고 벌점 때문에 순서가 바뀌는 예제: A와 B의 배정이 다르고, B의 주의 일수가 적다.
  - 부두-저탄장 연결, 정비 시작 금지와 하역 연장, ETA 전 금지, 고정 점유.
  - 체선료 없는 항차가 `gaps`로 빠지고 배정은 된다.
  - 같은 결과 안 합치기, 현재 계획 평가, 원인 판정 3종.
  - 재고 모름이면 A안만.
- **API**: 권한, 422 입력 검증, 저장 API를 부르지 않음.
- **npm test**: `src/domain/berth-plan.ts`의 응답 검증.
- **UI(Playwright, API 모킹)**: 안 카드 전환, 간트·표 표시, 가정값 표시, 적치 추천 열기, 오류 표시, 라이트/다크·390px.
- **ZGX 사본**: ZGX DB를 읽기 전용으로 복사해 로컬에서 60척 더미로 풀이 시간을 잰다(목표: 14일 30초 안).
