# 운영 질의 도우미 설계 (LLM + 계산 도구)

- 작성일: 2026-11-09 (KST)
- 상태: 초안, 사용자 검토 대기
- 선행 조건: PR runtosurvive0/genForecast#18 병합. 항차 원장(`voyage_registry.py`), 수급 도우미(`demo_assistant.py`), 대기 선박 후보(`vessels/waiting.py`)가 그 PR에 들어 있다.

## 1. 목적

담당자가 한국어로 묻는 운영 질문에 답한다. 예:

- "지금 당진 부두 앞에서 기다리는 배는?"
- "A호가 이틀 늦으면 5~8호기 재고일수는 며칠까지 떨어져?"
- "다음 2주 입항선 접안 순서를 체선료 최소로 짜 줘"
- "왜 3일 뒤 9~10호기가 주의로 나와?"

성공 기준:

1. 답에 나오는 모든 숫자는 계산 도구나 ZGX 자료에서 나온다. LLM이 숫자를 지어내지 않는다.
2. 숫자마다 기준시각(KST)과 출처(실측·계획·모의)가 붙는다. 실제 운영 정보와 합성·모의 값을 섞어 보이지 않는다.
3. 자료가 없거나 도구가 실패하면 "모름·자료 필요"로 답하고, 무엇이 비었는지 말한다.
4. 기본은 읽기 전용이다. ZGX 자료를 바꾸는 동작은 담당자가 화면에서 확인해야만 실행된다.
5. 평가 질문셋(7절)에서 도구 선택과 답의 수치가 기준을 통과한다.

범위 밖: 운임·시황 예측, 용선 계약 협상, 외부 웹 검색, 자동 실행(사람 확인 없는 계획 저장).

## 2. 현재 상태

| 있는 것 | 위치 | 이번 설계에서의 쓰임 |
|---|---|---|
| 지시 → 계산 조건 해석기 (지연·설비 정지·부하·상탄 전략, JSON 스키마 + 검증) | `backend/src/midterm/demo_assistant.py`, `web/assistant_api.py` | 가정 계산 도구의 입력 해석으로 흡수 |
| 재고·연소·입하 전망 엔진 | `supply.py`의 `simulate()` | 가정 계산·최적화 제약의 기준 |
| 실제 대기 시간 | `supply.py`의 `demurrage_hours` | 조회 도구 |
| 대기 선박 후보 (AIS 규칙) | `vessels/waiting.py` | 조회 도구 |
| 항차·선박·화물·분석 원장 | `voyage_registry.py` | 조회 도구, 최적화 입력 |
| HiGHS 솔버 래퍼 | `highs_backend.py` | 접안 일정 최적화 |
| 사용자별 호출 제한(분당 20회) | `assistant_api.py` | 그대로 재사용 |

빠진 것:

- 항차 원장에 **허용정박시간(laytime)·일당 체선료·체선 기산 규칙**이 없다. 지금은 `src/domain/control-tower.ts`의 데모 타입에만 있다.
- 부두 자료(`dangjin_berths.json`)는 위치 선분뿐이다. **부두별 하역 능력·수심·선형 제한**이 없다.
- 질문을 받아 여러 도구를 부르는 **대화 루프**가 없다. 지금 해석기는 한 번 호출해 조건만 돌려준다.

## 3. 접근 방식

검토한 세 가지:

1. **LLM이 자료를 받아 직접 계산** (프롬프트에 원장·재고를 넣고 답하게 함): 구현은 빠르지만 숫자가 검증되지 않는다. 최적화는 사실상 불가능하다. 채택하지 않는다.
2. **질문 유형별 고정 화면·버튼**: 정확하지만 "다양한 질문"이라는 목적에 맞지 않는다.
3. **도구를 부르는 에이전트 (채택)**: LLM은 질문을 해석하고 도구를 고르고 결과를 설명한다. 조회·계산·최적화는 ZGX 백엔드 함수가 한다. 기존 해석기의 원칙("LLM은 조건 해석만, 계산은 엔진이")을 그대로 넓힌다.

## 4. 구조

```
담당자 질문 ─▶ /api/assistant/ask ─▶ 에이전트 루프 (ZGX)
                                     │  LLM: 도구 선택·인자 작성
                                     ├─▶ 읽기 도구 ── ZGX DB (원장·AIS·재고·계획)
                                     ├─▶ 가정 계산 도구 ── simulate()
                                     └─▶ 최적화 도구 ── HiGHS
                                     ◀── 도구 결과(JSON, 기준시각·출처 포함)
                                     │  LLM: 결과만 근거로 답 작성
                    ◀── 답 + 근거 표 + 실행 가능한 제안(확인 버튼)
```

### 4.1 에이전트 루프 (`backend/src/midterm/assistant/agent.py`)

- 입력: 질문 문자열(최대 1,000자), 화면 맥락(현재 탭, 기준시각), 같은 대화의 이전 턴(최대 10턴).
- 루프: LLM 호출 → 도구 호출 요청이 있으면 실행 → 결과를 붙여 다시 호출. **최대 6회 도구 호출**, 전체 60초 제한. 넘으면 그때까지의 결과로 "일부만 확인됨"이라고 답한다.
- 출력 스키마(구조화 출력으로 강제):
  - `answer`: 한국어 답
  - `facts[]`: `{label, value, unit, as_of, source: "actual"|"plan"|"simulation"|"optimization", tool_call_id}`
  - `proposals[]`: 담당자가 누를 수 있는 동작(예: "이 일정을 반입 계획으로 저장"). 이 자체로는 아무것도 실행하지 않는다.
  - `gaps[]`: 답하지 못한 부분과 필요한 자료
- **숫자 검증**: `answer`에 나온 숫자가 `facts`의 값(반올림 허용)에 없으면 답을 내보내지 않고, 한 번 다시 쓰게 한다. 두 번째도 실패하면 `facts` 표만 보여 준다.
- LLM 제공자는 어댑터 한 곳(`assistant/llm.py`)에서만 다룬다. 지금 설정(`OPENAI_API_KEY`, `GENFORECAST_ASSISTANT_MODEL`)을 이어 쓰고, 도구 호출을 지원하는 다른 제공자로 바꿀 때 이 파일만 바뀐다. 키는 ZGX 환경 변수에만 둔다.

### 4.2 도구 (`backend/src/midterm/assistant/tools.py`)

모든 도구는 JSON 스키마로 인자를 받고, 결과에 `as_of`(KST)와 `source`를 넣는다. 인자 검증은 기존 `demo_assistant.validate()`처럼 허용 범위 밖이면 거절한다.

| 도구 | 종류 | 내용 |
|---|---|---|
| `list_voyages(status?, from?, to?)` | 읽기 | 당진행 항차: 선명, 상태, 계획·실제 입항·접안·하역완료, 부두 |
| `waiting_vessels()` | 읽기 | AIS 대기 후보와 담당자 확인 여부, 대기 시간 |
| `stock_snapshot(at?)` | 읽기 | 그룹별 재고 t, 발열량, 재고일수, 기준재고 시각 |
| `plan_for_day(day)` | 읽기 | 저장된 계획의 호기별 출력·순수요 |
| `simulate_scenario(changes[], horizon_days)` | 계산 | 기존 해석기 조건(지연·정지·부하·전략)을 넣은 재고 전망. 기준 전망과의 차이 포함 |
| `demurrage_estimate(voyage_nos[], schedule?)` | 계산 | 항차별 예상 대기시간과 체선료. 계약값이 없는 항차는 `null`과 사유 |
| `optimize_berth_schedule(from, to, objective, locks[])` | 최적화 | 5절 |

쓰기 도구는 만들지 않는다. 저장은 `proposals`로만 제안하고, 화면에서 담당자가 누르면 기존 저장 API(예: 반입 계획 저장)를 기존 권한 검사와 함께 부른다.

### 4.3 화면

- 위치: 상단바의 공통 질의 입력. 결과는 오른쪽 패널에 답, 근거 표(`facts`), 빈 자료(`gaps`), 제안 버튼 순서로 보여 준다.
- 최적화 결과는 접안 일정 간트와 "기존 일정 대비" 표로 보여 준다.
- 모의·합성 표시는 기존 규칙대로 상단 공통 모드 표시 한 곳에서만 한다. 근거 표의 `source` 열은 값의 출처를 적는 칸이고, 카드마다 모의 문구를 반복하지 않는다.
- 폴더: `src/features/assistant/`. 공통 타입은 `src/domain/assistant.ts`.

## 5. 체선료 최소 접안 일정

### 5.1 문제

- **집합**: 기간 안 입항 예정 항차 V, 부두 B(1~3), 시간 슬롯 T(1시간).
- **결정변수**: `x[v,b,t]` = 항차 v가 부두 b에서 t에 하역 시작(0/1).
- **제약**
  1. 각 항차는 한 번만 접안: Σ_b,t x[v,b,t] = 1
  2. 부두당 동시에 한 척: 하역 시간 `ceil(화물량 / 부두 하역능력)` 동안 겹치지 않음
  3. 도착 전 접안 불가: t ≥ 예상 도착(ETA)
  4. 선형 제한: 부두가 받을 수 없는 선박 조합은 0
  5. 하역 불가 시간대(기상·정비): 해당 슬롯 시작 금지, 걸치면 하역 시간 연장
  6. 그룹별 재고일수 ≥ `danger_days`(기존 설정값): 입하 시점이 재고 전망에 미치는 영향을 일 단위로 선형화해 제약으로 넣는다. 입하 배분은 항차 원장 `yard`를 쓴다.
  7. `locks[]`: 담당자가 고정한 항차·부두·시각
- **목적**: 최소화 Σ_v 일당체선료[v] × max(0, (하역시작 − ETA − 허용정박시간[v]) / 24h)
  - 보조항(선택): 재고일수가 `normal_days` 아래로 내려간 일수 × 벌점. 기본은 끔.
- **풀이**: HiGHS. 2주·10척·3부두·1시간 슬롯이면 변수 약 1만 개 규모다. 30초 제한, 넘으면 그때까지의 최선해와 간격(gap)을 함께 돌려준다.

### 5.2 결과

- 항차별 부두·접안·하역완료 시각, 예상 체선 시간·금액(USD)
- 기존 계획 일정 대비 차이와 총 절감액
- **걸린 제약 설명**: 체선이 생긴 항차마다 원인이 된 제약(부두 점유, 재고 하한, 하역 불가 시간)을 하나 이상 붙인다. LLM은 이 목록으로 "왜"를 설명한다.
- 계약값이 없는 항차: 목적함수에서 제외하고 `gaps`에 넣는다. 기본값을 추정해 넣지 않는다.

### 5.3 필요한 자료 (공통 데이터 계약 변경, 통합 담당자 합의 필요)

항차 원장 `voyages`에 추가:

| 필드 | 단위 | 설명 |
|---|---|---|
| `laytime_hours` | h | 허용정박시간 |
| `demurrage_usd_per_day` | USD/일 | 일당 체선료 |
| `laytime_start_rule` | 열거 | 기산 기준: `nor_6h`(NOR 후 6시간) / `arrival` / `berth` |

부두 자료에 추가(`dangjin_berths.json`과 프런트 사본을 같이 변경):

| 필드 | 단위 | 설명 |
|---|---|---|
| `unload_tph` | t/h | 부두별 평균 하역능력 |
| `max_loa_m`, `max_draft_m` | m | 선형 제한 |

하역 불가 시간대는 처음에는 담당자가 입력하는 목록으로 시작하고, 기상 예보 연동은 나중에 한다.

## 6. 오류·안전

- 도구 실패: 해당 도구 결과를 `{"error": "..."}`로 LLM에 넘기고, 답에 그 부분을 `gaps`로 드러낸다. ZGX 접속 실패를 로컬·합성 값으로 대신하지 않는다.
- LLM 미설정·실패: `/api/assistant/ask`는 503을 돌려준다. 화면은 "도우미를 쓸 수 없음"을 표시하고, 기존 규칙 기반 해석기는 그대로 동작한다.
- 프롬프트 주입: 원장 메모·선박명 같은 자유 문자열은 도구 결과 안의 자료로만 넘긴다. 쓰기 도구가 없으므로 주입돼도 자료를 바꿀 수 없다.
- 비용: 기존 사용자별 분당 20회 제한을 쓰고, 질문당 최대 토큰을 설정한다.
- 기록: 질문, 호출한 도구와 인자, 답을 ZGX DB에 90일 보관한다. 평가 질문셋을 만들 때 쓴다. 개인 식별 정보는 사용자 id만 남긴다.

## 7. 검증

- **도구 단위 테스트** (pytest, 격리 DB): 각 도구의 인자 검증, `as_of`·`source` 포함, 자료 없음 처리.
- **최적화 테스트**: 손으로 풀 수 있는 3척·2부두 예제에서 최적해와 체선료가 기대값과 같음. 재고 하한 때문에 순서가 바뀌는 예제. 계약값 없는 항차가 `gaps`로 빠지는 예제.
- **에이전트 테스트**: LLM 어댑터를 가짜로 바꿔, 도구 호출 순서·숫자 검증·6회 제한·도구 실패 처리를 확인.
- **평가 질문셋** (`backend/tests/assistant_eval/questions.jsonl`): 실제 담당자 질문 30~50개. 문항마다 기대 도구, 기대 수치 범위, "모름"이 정답인지를 적는다. 실제 LLM으로 돌리는 평가는 비용이 들어 CI에 넣지 않고, 배포 전 ZGX에서 수동으로 돌린다. 통과 기준: 도구 선택 90% 이상, 수치 오류 0건, 자료 없는 질문에 숫자를 지어낸 경우 0건.
- **UI 테스트** (Playwright, API 모킹): 답·근거 표·빈 자료·제안 버튼 표시, 제안 버튼을 누르기 전에는 저장 API가 호출되지 않음.

## 8. 단계

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| 1 | 에이전트 루프 + 읽기 도구 4개 + `simulate_scenario` + 화면 패널 | 조회·가정 계산 질문이 평가셋 해당 문항 통과 |
| 2 | 항차 원장·부두 자료 필드 추가(5.3) + `demurrage_estimate` | 팀 합의, 원장 화면·엑셀 가져오기에서 입력 가능 |
| 3 | `optimize_berth_schedule` + 간트 화면 | 7절 최적화 테스트 통과, 평가셋 최적화 문항 통과 |
| 4 | 평가셋 확장과 배포 전 수동 평가 절차 문서화 | 7절 통과 기준 충족 |

첫 구현 계획은 1단계만 다룬다. 2단계는 공통 데이터 계약 변경이라 별도 합의 후 계획을 쓴다.

## 9. 정해야 할 것

- LLM 제공자 유지 여부(지금 OpenAI). 4.1의 어댑터 구조라 나중에 바꿔도 된다.
- 체선 기산 규칙의 기본값과 실제 계약서 항목 이름 — 연료 담당 부서 확인 필요.
- 부두별 하역능력의 출처(설비 사양값 또는 최근 실적 평균).
