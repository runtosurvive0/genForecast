# SPEC v0.1 페이지 데이터 계약

**발전소 종합과 저탄장 현황**은 같은 MILP·DB 수급 조회 조건을 사용한다. 데이터 모드는
발전소 종합에서 선택하며 저탄장의 기존 약도·패널·원장 UI를 유지한다. 데이터/관리자에는 MILP 업로드 탭을 추가한다.
선박추적·모델 상세·정지계획·시나리오는 기존 기능을 유지한다. 아래 기존 SPEC 정의는 합성 데모와 기존 메뉴에 적용한다.
원본 `SPEC.md`는 수정하지 않았다.

## MILP 백엔드 조회 모드

- 화면 계약은 `src/domain/planning.ts`, 공통 조회 상태는 `src/domain/use-planning.ts`,
  조회 조건·출처·오류 표시는 `src/components/PlanningWorkspace.tsx`다.
  `GET /api/runs`로 저장 결과를 선택하고 `GET /api/planning/runs/{run_id}/snapshot?start=YYYY-MM-DD&horizon=30`
  으로 같은 계산의 호기·일별·월별·정비·모델·DB 수급 자료를 조회한다. 계산을 새로 실행하지 않는다.
- 조회 기간은 7/30/60/90일, 시간은 KST 00시~24시다. 발전소 ID는 `dangjin`, 호기 ID는
  `dj-1`~`dj-10`이며 서버의 `당진1`~`당진10`을 명시적으로 변환한다. 설비용량은 원장 기준이다.
- 이용률 = 조회기간 발전량 MWh / (설비용량 MW × 조회기간 전체 시간) × 100.
  발전계획을 프런트 모델 비율로 재조정하거나 재고 부족으로 축소하지 않는다. 현재 출력 실적은 제공하지 않는다.
- 전국 수요는 시간별 예측의 일평균/최대 MW다. 석탄 ML 필요발전량, 보정 목표, 전국 석탄 MILP
  발전량, 설비·정비에서 산출한 가용용량을 구분한다. 당진 발전량은 호기 계획에서 따로 집계한다.
- 일별·호기별·월별 구매 연료계획은 새 계산의 **저장 입력 기준 발열량**과 호기 열량곡선/수기 HR을 사용한다.
  발열량을 보존하지 않은 이전 결과는 현재 DB 설정을 사용한다.
  5,500 kcal/kg는 임시 가정으로 표시한다. 월별 값은 선택한 저장 계산의 전체 기간이며,
  한 달의 모든 시간계획이 없으면 월 합계가 null이다. 조회한 30일을 월 합계로 표시하지 않는다.
- DB 재고전망은 기존 Python 공통 수급 엔진을 사용한다. 처별 혼합 발열량을 반영하므로 고정 기준
  구매 연료량과 다를 수 있다. 미등록 기준재고는 null이며 위험도 미확정, 음수 재고는 계획상 부족량이다.
- 계획정지는 선택한 계산에 반영된 일정이다. 날짜만 입력한 종료일은 해당 날짜를 포함하여
  다음날 00시를 재가동 시각으로 전달한다. 일정 미등록은 무정비 확정을 의미하지 않는다.
- 새 저장 결과는 `coal_available`와 `unit_capacity_mw`를 보존한다. 이전 결과의 미보존 가용용량은
  null, 설비용량은 현재 원장으로 계산하고 확인사항에 출처 차이를 표시한다.
- 계산 분류, 저장시각, 원장 최신성, 계획 범위 부족을 그대로 표시한다. 합성 학습 손실이나
  검증지표를 실제 모델 값으로 대체하지 않는다. API 실패 시 합성 데모로 자동 전환하지 않는다.
- MILP 입력·실행은 데이터/관리자의 업로드 탭에서 관리한다. 실제 AIS/Pile/실적 수집은 별도 연결이 필요하다.
- 연료 대시보드(`src/features/plant/FuelDashboard.tsx`)는 같은 조회 계약을 사용한다.
  기간 연료 합계·일평균·최대 일 사용량은 조회기간의 모든 날짜에 연료계획이 있을 때만 표시한다.
  누락은 미확정, 계획량 0은 0으로 유지한다. 실적 연료사용량은 미연계로 표시한다.
- 월별 차트는 전체 계산기간의 온전한 월 합계이며, 조회기간과 겹치는 월만 강조한다.
  호기별 비중은 10개 호기의 예정량 합계를 분모로 사용하며, 합계가 0이거나 누락이면 미확정이다.
- DB 등록 입하 예정량은 조회기간 내 처별 하역 배분의 합계다. 수급 원장의 혼합 발열량 기준 재고전망과
  구매계획용 고정 발열량 기준 소비량을 단순 가감해 새 재고전망을 만들지 않는다.
  호기 정지 건수는 조회기간과 겹치는 등록 일정만 센다.
- 첨부 화면을 반영한 상단 요약·3개 처별 표·연료 흐름도·전망은 `FuelSupplyOverview.tsx`가 담당한다.
  총 재고·하역 잔량·입항 예정 화물량·입항탄 가중평균 열량은 Python 공통 수급 엔진의 KPI다.
  위험/안정 재고일수 기준은 snapshot의 `inventory.thresholds`로 전달하는 DB 설정이다.
  처별 현재 재고·혼합 열량·기준대비 증감·입하 배분을 호기별 **조회기간 평균** MW와 t/h와 구분한다.
- 전국 모델 차트는 일평균 수요·태양광·석탄 ML·MILP·가용용량을 GW로 표시한다.
  태양광은 독립 ML 모델이 아닌 패턴 전망이며 검증 MAPE를 임의로 만들지 않는다.
  핵심 지표와 첫날 연료계획의 날짜는 조회 시작일이다. 실제 현재/금일이나 내일로 표시하지 않는다.

## 종합·저탄장 공통 수급 조회 (2026-10-12)

- App이 계산 ID·조회 시작일·기간과 한 snapshot을 소유한다. 탭 이동으로 초기화하지 않는다.
  당진 DB 수급만 제공하며 다른 발전소를 포함한 합계는 미확정으로 유지한다.
- 발전소 종합의 데이터 모드를 저탄장에서도 따른다. 저탄장 화면의 약도·패널·KPI·원장·분석·
  전망 UI는 유지하고 데이터만 연결한다. 저탄장에 별도 DB 화면이나 조회 컨트롤을 추가하지 않는다.
- 종합 KPI 버튼은 기존 저탄장 원장·처 패널·재고 전망·입하 타임라인으로 이동한다.
  저탄장 기존 기간 버튼으로 공통 조회 기간을 바꿀 수 있고 종합으로 돌아와도 유지한다.
- `supply-view.ts`는 Python 수급 결과를 기존 저탄장 표현으로 변환한다. 재고 엔진을 복제하거나
  DB 재고를 샘플 Pile에 배분하지 않는다. 기준시각 재고일수와 기간 최소값을 구분하며,
  경고 기준·미확정·최신성은 snapshot을 따른다. 수요 0과 자료 누락을 같은 상태로 확정하지 않는다.
- 총 저탄량과 처별 헤더·패널·재고전망은 DB 처별 재고다. 실제 Pile 원장이 없으므로 약도와
  Pile 상세·탄질·원장은 기존 SIMULATED 표본을 유지하고 해당 출처를 표시한다.
- 저탄장 입하 예정량은 기간 내 처별 하역 배분량이다. 종합의 입항 예정량은 해당 기간에 입항하는
  선박의 전체 화물량이다. 입항량·입고량·하역 잔량을 혼용하지 않는다. DB 미완료 화물을 기존
  타임라인에서 조회하며 접안·하역 완료시각과 처별 일별 하역 반영량은 백엔드 제공값을 사용한다.
  하역 완료시각은 마지막 속도·누적량의 예상값이다. 속도가 0이면 임의 완료시각을 만들지 않는다.
- 하역 잔량 KPI는 하역중 선박만 집계한다. 기존 선박·이탄 원장 저장 성공 후 공통 snapshot을
  재조회한다. 누적 하역량 보정은 보정시각까지 유효한 하역율·배분을 유지한다.
- 하역 기본값은 선박별 **7,000 t/일 = 7,000/24 t/h**의 계획 가정이다.
  `POST /api/supply/vessels`에서 rate(t/h)를 생략하면 적용하고, 명시한 속도·0(중단)은 유지한다.
  `vessels.unloading_rate_tpd`는 조회시각의 하역율, `today_receipts`는 조회 KST 날짜에
  실제로 전망 재고에 반영하는 하역량이다. 접안시각·중단·Cargo 잔량을 반영하므로 항상 7,000t인 것은 아니다.
  부두별 컨베이어에 두 값을 따로 표시하며 빈 부두·미접안 선박에는 자동 입고를 만들지 않는다.
- 가상 하역 원장은 `run_id`와 `classification=simulation`을 함께 지정한다.
  계산 기간 안의 하역 시작과 원장 중복을 검증하며, 같은 요청 재전송은 같은 ID를 반환한다.
  다른 MILP 계산과 기본 운영 원장 조회에는 섞지 않는다. `/api/supply/records?run_id=`로 조회한다.
  원장에 연결된 표본 선박은 조회일의 DB 상태를 따르고 하역 완료 후 약도의 접안선에서 제외한다.
- 미등록 재고는 null, 음수 전망은 계획상 부족량이며 API 실패를 표본 수치로 대체하지 않는다.
  재고·입하 값과 기준일은 선택 계획 시점으로 표시하며 현재 운전 실적과 구분한다.
- 사용자가 지정한 저탄장 Pile 배치(가로×세로): P1 5×4, P2 5×4, P3 10×2. 처별 20개와
  4개 탄종 구역을 유지한다. P3은 두 구역씩 한 행에 놓으며 방향키도 실제 열 수를 따른다.
- 약도 상단은 1발전처(1~4호기)·2발전처(5~8호기)·3발전처(9~10호기)로 나눈다.
  `daily.unit_generation_mwh`는 선택한 MILP 날짜의 호기별 MWh이며 처별로 합산한다.
  상탄량은 같은 날짜의 `inventory.daily.groups[*].burn`(혼합 열량 기준 t/일),
  t/h는 이 값을 24로 나눈 **일평균**이다. 기존 표본 순간 게이지를 MILP 값으로 혼용하지 않는다.
  상탄 컨베이어도 처별로 분리해 같은 t/h를 각 처의 발전소와 저탄장 사이에 표시한다.
  조회 시작일·KST·MILP/샘플 출처를 표시하고 누락은 미확정, 실제 0은 0을 유지한다.
- 이탄벨트는 1↔2·2↔3의 인접 저탄장 사이에 표시한다. 좁은 화면에서는 세로로 배치된
  저탄장 사이에 표시한다. 실제 설비 계통·가동 확인값이 아닌 연결 개념도다.
  하역선·Pile·패널·키보드 이동과 기존 이탄 원장 기능을 유지한다.

## MILP 업로드·DB 실행·가상 시작재고 (2026-10-12)

- 기본 작업 DB는 `backend/data/planning-local.sqlite3`. 최초 실행 시 공개 승인된
  `planning.sqlite3`를 SQLite backup으로 복사하고 이후 원본을 변경하지 않는다.
  `MIDTERM_PLANNING_DB` 환경변수로 경로를 지정할 수 있다. 작업 DB와 새 결과는 Git 제외다.
- 2026-10-13 사용자 공유 요청으로 `backend/seeds/fuel-integration-2027.sqlite3`를 추가했다.
  `python -m midterm seed-demo`로 작업 DB에 가상 입력 1건·완료 결과 1건·처별 기준재고 3건·
  고/저 재고 6건·BD-1 가상 하역 1건을 원자적으로 등록한다. 계정·세션·AIS·실적은 포함하지 않는다.
  기존 데이터를 덮어쓰지 않으며 내부 ID를 다시 연결한다. 중복은 건너뛰고 시각/계산 ID 충돌은 취소한다.
  MILP 결과는 `functional_demo`, 원장은 `simulation`이다. 조회 시작일은 2027-01-01 KST다.
  공용 ZGX에는 별도 명령 실행이 필요하다. 공개 범위·체크섬은 `shared-assets.json`에 추가 기록했다.
- `POST /api/planning/inputs/upload`는 multipart의 `scenario` JSON, `heat_prices` CSV/XLSX/CSV JSON 사본을
  필수로 받으며 `coal`·`nuclear` 정비 파일은 선택이다. 파일별 최대 4MB, 알려진 호기·정비 날짜·기간·
  12개월 보정·단가의 유한성/양수를 검증하고 전체 검증 통과 후에만 저장한다.
- `milp_inputs`는 시나리오·정비·월별 열량단가·기준 발열량·파일명/체크섬을 보존한다.
  업로드·가상 시작재고·항내 입출항 원장 쓰기는 승인된 관리자 세션과 CSRF 검사를 요구한다.
  `POST /api/run {input_id}`는 이 입력을 사용한다. 단가 파일을 바꿔치기하지 않는다.
  `milp_runs`는 입력 ID·실행 상태·실패 원인·완료 요약 JSON·전체 시간별 NPZ BLOB을 저장한다.
  `GET /api/planning/inputs`, `/inputs/{id}`, `/executions`, `/api/job`로 조회한다.
  DB 결과는 파일이 없어도 `run_plan()`으로 다시 조회할 수 있다. 기존 파일 결과도 계속 지원한다.
- MIP/MILP는 미래 **예측 시뮬레이션**이다. 내부망 발전 실적은
  `POST /api/supply/plans`의 `source=API`, `classification=observed_generation`으로 별도 저장한다.
  `as_of` 이전에 완료된 정각 1시간 구간의 평균 MW와 당진 호기를 전달한다.
  실제 내부망 수집기는 아직 연결하지 않았다. 열량곡선 또는 호기 HR로 발전량에서 연료소모를 역산하며,
  실측 연료계량과는 구분한다. 누락 호기를 0으로 채우지 않는다.
- `POST /api/supply/simulation-stock`은 DB에 완료된 계산 ID를 받아 그 계산 시작일 00:00 KST에
  가상 시작재고를 등록한다. 미래 가상 재고를 운영 수기 기준재고로 등록하지 않는다.
  기존 `/baselines`는 과거 운영 기준재고만 받는다. 조회 시 다른 계산의 가상 재고를 제외한다.
- `supply_stock_lots`는 처·고/저열량·톤·발열량·가정 여부를 저장한다.
  초기값: 1처 고 50,000/저 90,000t, 2처 고·저 각 100,000t, 3처 고·저 각 150,000t.
  사용자 가정 열량 고 6,000/저 5,000 kcal/kg. 처별 혼합 열량은 1처 5,357.142857,
  2·3처 5,500 kcal/kg다. `initial_lots`는 시작 원장이고 현재 고/저 잔량을 뜻하지 않는다.
  Pile 적치 위치와 탄종별 소비 우선순위는 미지정이므로 임의로 만들지 않는다.
- 처별 재고 = 시작재고 − 열량곡선/HR 기반 연료소모 + 하역 배분량 ± 처간 이탄.
  `inventory.daily.groups[*].receipts`는 해당 KST 날짜의 하역 배분·누적 보정량이다.
  이 DB 엔진은 하역 중 시간별 반영을 사용하며 합성 데모의 완료일 일괄 반영과 구분한다.
- 선박 원장은 MMSI/IMO·BD-1/2/3·고/저/혼합 탄종을 선택 저장한다.
  `POST /api/supply/port-visits`는 source/event_id로 중복을 방지하며 등록된 vessel_id(화물)에
  입항·접안·출항 관측을 연결한다. AIS 위치만으로 Cargo를 만들거나 자동 원장 등록하지 않는다.
- `supply_port_visits`는 AIS 입항·체선 이력이다. `waiting_cargo`(체선 화물),
  `port_remaining`(항내 선박 잔량), `stock_including_port`(저탄장+항내 잔량)를 별도 제공한다.
  저탄장 stock에는 하역된 물량만 포함한다. 미접안 관측은 지난 하역 예정시각의 가상 입고를 막는다.
  체선 시간은 관측 입항부터 접안(미접안 시 조회 시각)까지이며 계약상 체선료는 계산하지 않는다.

## 식별자와 원천

- 발전소 내부 `Plant.id`는 API의 `plant_id`와 동일 값이다. 당진 `dangjin`, 보령 `boryeong`, 하동 `hadong`, 동해·삼척 `donghae`.
- `src/data/control-tower.ts`의 `Stockpile.stockpile_id`, `plant_id`, `on_hand_t`, `calorific_value_kcal_kg`, `moisture_pct`, `ash_pct`, `sulfur_pct`, `stacked_at`, `temperature_c`, `co_ppm`, `eligible_unit_ids`가 Pile 원장이다. 센서 두 필드는 null이며 위험도는 `pileRisk()`가 적치기간과 탄종만으로 계산한다.
  `인니 저열량탄`(4번째) Pile은 혼탄 전용이라 `eligible_unit_ids`가 1,000MW 호기만 포함한다. 저탄장 화면은 이를 ‘혼탄’으로 표시하고 주간 소진 시뮬레이션에서 해당 호기 수요만 배분한다.
  당진 전용: `berth_id`(BD-1·2·3)→`plant_yard`(P1·P2·P3) 1:1 고정 매핑. 탄종 기준 Pile 귀속(DA-01·DA-03→P1, DA-02→P2, DA-04→P3), P2·P3 `indoor:true` 옥내 뱃지. 하역분은 탄종 일치 Pile에 귀속해 30일 이력을 하역일 역순으로 표시한다. 상탄 게이지는 현재 출력의 t/h 환산치이며 전망 대비선은 요청 연료다. 이탄 가용(`transfer_capacity_t`)은 표본 임의값, 이송량은 수기 입력·초과 경고만. 저탄장 진입 기본값은 당진이다. 모두 SIMULATED 표본이다.
  접안 확장: 당진 60개 Pile(기존 4개 유지 + 56개 추가, 총량 증가, 처별 20개·2x2 탄종 구역×5개·구역 탄질 계승, `zone` 0~3). 최상단은 당진 항만·저탄장 약도 + 우측 선박 패널. 도착 판정은 실제 현시각 ETA·당진행 한정. 접안은 선박 패널에서 부두 선택 후 버튼으로 지정, ETA순 추천 뱃지·사유 표시, 점유 데이터 없음. 합계 단언은 scope 변경 사유로 갱신한다.
  항만·저탄장 약도: 앞바다·부두·하역 컨베이어·처별 저탄장·상탄 컨베이어·발전소를 한 카드(`StockyardSite`)에 이어 그린다(방파제 없음, 측량 좌표 아님). 하역중 선박은 실효 부두(접안 지정 > `berth_id`)에 안벽과 평행하게 접안하고, 해상 대기선은 ETA순으로 묘박지에 둔다. 더미 AIS(`source: "dummy"`) 동안 ‘예시 대기선’ 1척을 실제 대기선 뒤에 항상 표시하고, 실시간 AIS(`aisstream`) 연결 시 숨긴다. 예시 대기선은 항차 데이터가 아니며 선택·집계에서 제외한다. 상탄 t/h는 발전소로 들어가는 컨베이어에 표시한다. Pile 둔덕 폭·높이는 재고의 세제곱근 비례, 하역 이력·예정은 Pile 배지(건수)와 마우스오버 툴팁·선택 상세로 보이며 별도 목록은 없다. 위험도 필터는 약도 Pile을 숨기지 않고 흐리게 한다. 모두 SIMULATED.
  처 단위 재고(2026-10-10): 처 소속 호기는 호기 번호로 P1=1~4, P2=5~8, P3=9~10(백엔드 `supply.py` `UNITS`와 동일, `/api/supply` 처 ID `g14·g58·g910` 매핑). 처 사용량 = 발전소 `simulate()` 일별 요청 연료 × 소속 호기 계획 발전량 비중이며, 처별 부족 전까지 처 합계는 발전소 엔진 재고와 같다. 재고일수 = 재고 ÷ 첫날 사용량(현재), 일말 재고 ÷ 다음 7일 평균(기간), 상태 기준은 SPEC §13 20/30일. 표본 당진 호기는 1·2·9호기라 2발전처는 "소비 없음"이다. 하역 귀속은 실효 부두(접안 지정 > `berth_id`)의 처 안 같은 탄종 Pile로 먼저 좁히고, 없을 때만 발전소 전체로 넓힌다. 주간 소진은 처별 7일 사용량을 그 처 Pile·소속 호기 기준으로 배분한다. 이탄·접안 지정은 화면 모의로 처별 전망·귀속에 반영하며 기준시각 이전 이탄은 제외한다. 이탄 저장은 `/api/supply/transfers`. `pileRisk`는 `temperature_c`·`co_ppm`이 있으면 임시 구간 점수를 더하고 출처를 SENSOR로 표시한다. 실시간 AIS(`/api/v1/vessels`)·센서(`/api/v1/stockpiles/sensors`)는 클라이언트만 있고 서버 미구현이며, 실패 시 더미를 유지한다. 전망 기간은 앱 30/60/90일 선택을 따른다.
- `Voyage.voyage_id`, `destination_plant_id`로 화물을 발전소에 연결한다. 로컬 페이지 표본은 한 항차에 한 화물이며 `cargo_t`가 API `cargo.quantity_t`에 해당한다. API DTO는 `src/domain/contracts.ts`의 CargoContract와 구분된다. 데이터 내보내기는 현재 로컬 표본 형식이다.
- MMSI `999000001` 등의 번호와 `DEMO-*` IMO는 시연용 식별자다. 지도와 상세정보는 동일한 좌표를 사용한다. 새 위치는 VesselMap의 positions 입력으로 전달하며, 온라인·오프라인 예시 항로도 같은 입력 좌표를 통과한다. 알려진 표본의 전후 경유점을 연결하는 시각 표현이며 실제 운항 이력이나 항해용 경로가 아니다. 알 수 없는 항차에 예시 항로를 생성하지 않는다.
- API/MILP 경계는 `src/domain/contracts.ts`, AIS Provider/decoder 경계는 `src/domain/ais.ts`. 네트워크 서비스는 실행하지 않는다.

## 단위와 시간

- 재고/화물/연료: t. 발전량: MWh 또는 GWh. 출력/용량: MW. 열량: kcal/kg. 수분/회분/황분: %. SOG: kn. COG: degree. 거리: nm.
- 일별 `date`는 09:00 KST 시작일이다. 재고는 다음날 09:00의 기말 재고이며 차트 가로축은 기말 시각 날짜를 표시한다. 입하·연료는 직전 24시간 집계다. 월 집계는 구간 시작일의 월로 묶으며 선택 기간에 포함된 구간만 합산한다.
- 하역이 전망 종료시각과 정확히 일치하면 마지막 기말 재고에 포함한다. 전망 시작 전 하역량은 현재 Pile 재고에 이미 포함된 것으로 간주한다.
- 현재 재고일수 = Pile 재고 / 첫날 예상 연료수요. 미래 재고일수 = 기말 재고 / 이후 7일 평균 계획 연료수요. 마지막 전망일을 위해 7일을 추가 계산한다. 0수요는 null(소비 없음). 최소 재고일수 날짜도 기말 시각이다.
- 실제 발전·소비는 재고로 제한하며 계획 수요는 보존한다. 발전소 간 재고를 공유하지 않는다. 혼탄 품질 변화는 아직 시뮬레이션하지 않고 현재 Pile 가중평균 열량·효율을 전망 기간에 고정한다.
- 효율 기준 환산과 heat-rate 기준 환산은 동치다. `heat_rate_kcal_kwh = 1 / (0.001163 * efficiency)`. SPEC 예시 `10000 * 2200 / 5500 = 4000 t`를 별도 검증한다.
- 현재 출력·이용률은 기준시각의 부하 표본과 계획정지를 사용한다. 미래 모델/시나리오가 현재 표본을 바꾸지 않는다. 7일 이용률은 가동 가능 시간의 정격용량을 분모로 한다. 호기 계획표는 연료 부족 전 계획값이며 실제 연료 제한 결과는 일별 재고 엔진에 반영된다.

## 모델

- 실제 로컬 경사하강법 선형회귀. 150일 train / 이후 30일 validation. 검증 표본을 gradient에 사용하지 않는다. 표시 손실은 정규화 MSE, MAE/RMSE 단위는 MW, MAPE는 %.
- 30/120/300회 반복을 선택해 재학습. 평균수요·최대수요·석탄가용용량 모델을 각각 학습한다. 마지막 관측일은 2026-10-05이며 D+1은 2026-10-06이다.
- 합성 데이터의 주기·추세 feature를 사용한다. 실제 기상·전력시장 자료와 연결되지 않았다. 예상 수요/기준 수요 및 예상 용량/기준 용량 비율을 호기 기준 부하에 곱한다. 정격용량·계획정지 제한을 적용한다. 계통 최적화가 아니다.

## AIS / ETA

- 온라인 선박 지도는 MapLibre + OpenFreeMap(OSM 기반) 상세 지도를 사용하며, 기본 지구본과 메르카토르 평면 보기를 전환할 수 있다. 평면용 도트는 투영 좌표에서 균일하게 샘플링하여 고위도 줄무늬를 방지한다. 도트→면 전환은 확대 배율에 따른 시각 표현이며 관측 데이터의 변경이 아니다. 외부 타일의 상세도·최신성은 지역별로 다르다.
- 실제 관심 선박은 서버 AIS 관측을 표시하고, 합성 표본은 별도로 표시한다. 단일 HTML 오프라인 실행 또는 초기 지도 연결 실패 시 로컬 SVG 도트 지도를 표시한다. 연결 후 일부 타일 요청 실패는 현재 지도·배율을 유지하고 안내와 타일 재시도를 제공한다.

- 최신성은 기준시각이 아니라 현재 컴퓨터 시각과 수신시각 차이로 계산한다: 10분 이내 LIVE, 60분 이내 RECENT, 360분 이내 ESTIMATED, 이후 STALE. 미래·잘못된 시각도 STALE. 고정된 10월 6일 표본은 시간이 지나면 모두 STALE다.
- ESTIMATED는 최신성 구분이며 이 버전은 위치 외삽을 수행하지 않는다. 지도에는 항상 마지막 표본 위치만 표시한다.
- 합성 항차 ETA는 등록 계획에 기상·항로·시나리오 지연을 더한다. 실제 선박의 기본 ETA는 유효한 AIS 속도와 예상 잔여 해상거리로 계산하며, 기상 보정은 가정값을 공개한 시연 모델이다. 오래된 위치·정지·불확실한 항로에서는 계산을 보류한다. 접안·하역 완료·재고 원장은 자동 변경하지 않는다.
- 체선료는 max(항만 대기 − 허용시간, 0) × 일 요율 / 24의 단순 예제이며 계약 정산이 아니다.
- [AISstream 공식 문서](https://aisstream.io/documentation)에 따라 키는 서버에 보관하고 브라우저 직접 연결을 하지 않는다. decoder는 사용할 수 없는 좌표와 SOG/COG sentinel을 거른다. 서버는 재연결·관심 선박 항적의 SQLite 보존을 담당한다. 수집 시작 전 항적은 제공하지 않으며 GFW 과거 기항은 별도 조회다.

## 현재 제공되지 않는 것

온라인 앱은 관리자 승인형 로그인과 회원/관리자 API 권한을 적용한다. 계정별 관심 선박·항차·목적항 설정은 별도 `access.sqlite3`에 버전과 함께 저장하며 공용 발전소·재고 원장 계약은 변경하지 않는다. 설정은 [ACCESS_SETUP.md](ACCESS_SETUP.md)를 따른다.

선박별 검증된 항해 성능 모델, 확정 운항계획·화물 자동 연계, 실제 센서 연동, 24시간 운영 보장은 제공하지 않는다. AIS·기상·GFW는 제공처 수신 범위·이용 조건과 자료 공백의 영향을 받는다. 발전소의 저장 MILP 조회와 선박 POC를 전체 SPEC 완료로 간주하지 않는다.

## 실제 선박 검색 관측 (2026-10-09 추가)

관심 선박 `TrackingVessel.source`는 기존 `demo | manual` 외에 `aisstream | digitraffic`을 허용한다.
실제 제공처에는 선택적 `ais` 관측이 연결되며, 새 실제 선박 등록 시 관측 객체와 MMSI가 필요하다.
`ais.updatedAt`은 선박 정보 기준 시각, `ais.position.observedAt`은 **위치 관측 기준 시각**이다.
정적 정보 수신만으로 위치 최신성을 갱신하지 않는다. 속도 `sogKn`은 kn, 진행방향 `cogDeg`는 degree,
좌표는 WGS84 경위도, 미수신·AIS sentinel은 `null`이다. AIS 목적지 문자열은 확정 목적 발전소가 아니다.
`shipType`과 `navStatus`는 AIS 원래 코드이며 미수신은 null이다. 화면은 시각을 KST로 표시한다.
Digitraffic REST의 `timestampExternal`과 metadata `timestamp`는 ms이며 AIS `timestamp`(초 필드)를
epoch로 사용하지 않는다. 이 관측은 팀 Voyage/Cargo/입하 원장을 자동 생성하거나 수정하지 않는다.
저장 형식은 workspace v1의 선택적 필드 확장으로 기존 저장 목록을 유지한다.
