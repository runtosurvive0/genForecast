# gen4cast 화면 구성과 단계별 작업 계획

이 문서는 화면과 작업 범위를 검토하기 위한 계획이다. 구현 완료나 실제 운전정보 연동을 뜻하지 않는다.

## 2026-11-08 데이터 적용 범위 정정

### 업무 범위 구체화

사내 화면은 필요한 구조를 이해하기 위한 참고이며 모든 입력 항목을 복제할 요구사항이 아니다. 레이캔·인코텀즈·장기용선 등 용선 구분은 핵심 입력에서 제외한다. 기존 DB 필드의 삭제·마이그레이션 여부는 별도로 검토하며, 이 문서 변경으로 이미 삭제된 것은 아니다.

핵심 업무 흐름은 **급전 출력 계획 → 호기별 석탄 사용 전망 → 현재 재고의 지속 가능 기간 → 입항 예정 화물 반영 → 적치·이적 배치안 비교**다.

- 발전·수급 전망: 출력 계획과 호기별 연료 조건을 바탕으로 저탄장별 소비·고/저열량탄 잔량 및 부족 시점을 확인한다. 현재 재고만 사용하는 경우와 예정 입하를 포함하는 경우를 구분한다. 공개 KPX 전망을 실제 급전 지시로 표시하지 않는다.
- 입항·화물: 선박, 도착 예정, 물량, 탄종·성상 및 연결 대상처럼 배치 판단에 필요한 정보를 입력한다. 계약 관리용 필드를 필수로 요구하지 않는다.
- 배치 추천: 도착 시점의 예상 잔량·사용 가능 공간과 고/저열량탄 목표 구성을 비교해 저탄장·Pile별 배분을 제안한다. 부두별 반입 경로와 호기 공급 경로를 준수한다.
- 대안 비교: 직접 배치로 목표 구성을 맞출 수 없으면 이적 가능한 경로를 이용하는 배치안을 제시한다. 출발·도착 구역, 물량, 예상 구성 변화와 충족하지 못한 조건을 함께 보여준다. 가능하지 않은 경로를 임의 생성하지 않는다.
- 이전에 요청한 저장기간 내 소진 가능 여부도 배치안에 포함한다. 사용자가 배분을 바꾸면 같은 입력·계산 흐름에서 결과를 재계산하고 계획을 저장한다.

확인해야 할 정책은 고/저열량탄 분류 기준, 목표 비율의 산정 기준과 저탄장별 목표·허용 범위다. 해당 값은 확인 전 고정하지 않는다. 모의 설비 경로·용량은 편집 가능한 설정으로 관리하며 실제 사내 설비정보로 주장하지 않는다.

사용자가 확정한 경계이며, 아래 과거 진행 기록의 사내 자료 등록을 앞으로 유지한다는 뜻으로 해석하지 않는다.

| --- | --- | --- |

제공된 사내 자료는 구조와 필요한 정보 항목을 이해하기 위한 참고이며, 실제 값·설비정보·첨부 원본을 제출 데이터로 사용하지 않는다. 실제 값의 소폭 변경이나 모의 분류만 붙이는 것으로 대체하지 않는다. 공개 데이터까지 가상 값으로 바꾸지는 않는다. 표시 정책은 공통 상단 모드 표시와 데이터 연결관리에 모으고, 각 화면에 시연 관련 문구를 반복하지 않는다.

선행 정리 대상은 `src/data/fuel-reference/`의 기준 자료, 관련 도면·운전 엔진·테스트의 인용 값, 공용 원장의 기준재고·화물·배분 및 그 이력이다. 기준재고 조회는 `src/domain/use-yard-baseline.ts`에서 API로 연결되며, `backend/src/midterm/stock_baseline.py`는 과거 revision도 보관하므로 최신 값 교체만으로 과거 자료가 제거되지는 않는다. 이 목록은 점검 시작점이며 전체 오염 범위를 확인한 결과는 아니다. 공용 DB·백업·제출 산출물의 정리는 아직 검증되지 않았다.

**완료 기준:** 내부 정보 없는 가상 시나리오를 DB·조작반에서 편집하고, 공개 KPX·AIS와 결합해 입력 → 저장 → 발전·연료 계산 → 도면·전망·혼탄 결과까지 일관되게 동작한다. 데이터가 모의라는 이유로 기능을 축소하지 않는다.

## 2026-11-08 작업 목적 재정립

사용자가 명시한 이번 통합의 목적은 다음 세 가지다. 아래 기존 화면 구성안과 진행 기록도 이 목적을 기준으로 해석한다.

1. 코드에 고정되어 추가·수정할 수 없던 데이터를 DB로 옮겨 사용자가 관리할 수 있게 한다. 저장뿐 아니라 조회·추가·편집·검증·이력과 실제 소비 화면까지 연결한다.
2. 각 기여자가 만든 정보와 업무 기능을 보존하면서 그래프·디자인 테마·메뉴·입력 방식을 하나의 디자인 시스템과 업무 흐름으로 통합한다. 화면에 어떤 정보가 있고 무엇을 바꿀 수 있는지 분명해야 한다.
3. 발전전망 팀의 기존 앱과 계산 계획을 기반으로 석탄 입하·재고·성상·사용을 발전전망에 연결하여 시스템 전체의 조건 변경과 결과 비교를 가능하게 한다.

화면 교체, DB 저장 성공, 개별 계산 성공만으로 통합 완료라고 하지 않는다. **업무 입력 변경 → 저장 → 계산 반영 → 관련 화면의 일치하는 결과**를 검증해야 한다. 기존 기능을 없애거나 축소하기 전에는 원래 목적·입출력·조작·저장 범위와 새 위치를 대조한다. 기존 가정이나 잘못된 연결까지 복원하지는 않으며, 의미가 불분명한 계약은 임의로 결정하지 않는다.

### 계산 통합에서 먼저 풀 경계

`docs/MIDTERM_INTEGRATION.md`는 기존 React 계산과 Python 발전전망의 차이를 이미 기록하고 있다. 기존 문서의 당시 로컬 서버·샘플 운영 절차는 현재 공용 ZGX 규칙을 대체하지 않는다.

- 호기 식별자, 일별 집계 경계, 기준재고 원천, 열소비율/발열량에 따른 연료 환산을 확인한다.
- 기존 React는 연료 부족 시 발전을 제한하는 계산이고, Python 계획 조회는 계획 소비 후 음수를 부족량으로 나타낸다. 두 의미를 UI 통일 과정에서 섞지 않는다.
- 실제 재고와 계획 입력의 기준시각을 보존하고, 기준재고에 포함된 입하를 다시 더하지 않는다.
- 우선 기존 발전계획 → 연료 필요량 → 입하·재고 전망을 일관되게 연결한다. 재고·혼탄 제약이 발전 최적화 자체에 역으로 반영되는지는 원래 계산의 지원 범위를 확인해야 하며, 연결되었다고 미리 주장하지 않는다.

### 후속 작업 순서와 완료 조건

1. **고정값·편집 가능 항목 이관표**: 기존 입력/상수/결과를 구분하고 현재 DB 필드, API, 편집 화면, 소비 화면을 대응시킨다. 부족한 정보는 질문하고 계산 결과를 입력값처럼 편집하게 만들지 않는다.
2. **발전·수급 전망의 기준 통일**: 발전전망 팀의 원래 입력과 실행·결과를 기준으로 메인, 정지계획, 시나리오의 데이터 흐름을 통일한다. 같은 조건 재조회와 조건 하나 변경 후 결과 비교를 격리 환경에서 확인한다.
3. **석탄 수급 연결**: 배선·입고·하역·이탄·Pile·대표 성상을 같은 식별자로 연결한다. 관련 원장 변경이 수급 전망·혼탄에 반영되고 중복 계상되지 않는지 확인한다.
4. **업무 화면 통합**: 위 기능 이관표를 기준으로 공통 제목·탭·검색·편집·저장·차트·상세 패널을 적용한다. 각 화면에서 무엇을 확인하고 무엇을 수정할 수 있는지 표시하고 대상·기간을 화면 전환 후에도 유지한다.
5. **전체 흐름 검증**: 공용 자료를 테스트로 변경하지 않고, 격리 DB에서 입력→저장→계산→비교→상세 확인을 검증한다. 기존 기능별 대체 위치와 검증 결과가 채워지기 전에는 이전 기능 이관 완료로 처리하지 않는다.

기존 하단 진행 기록은 당시 수행한 부분 작업의 기록이다. 위 항목 전체가 완료되었다는 의미가 아니다.

## 목표와 원칙

발전·연료 수급 전망을 시스템의 중심에 두고, 항차·화물부터 접안, 적치, 상탄·혼탄, 연소 및 구매 검토까지 전망의 근거와 다음 결정을 이어서 볼 수 있게 한다. 각 화면은 하나의 질문과 주 작업을 중심으로 구성하고, 등록·원장·상세는 그 작업에서 자연스럽게 연다. 정확한 회계금액 관리는 범위에 넣지 않는다.

- 기존 저탄·재고 화면의 공통 패널, 색상과 정보 밀도를 출발점으로 사용한다. 1920×1080에서 운영 현황의 핵심과 도면을 한 화면에 배치하고, 긴 원장·상세는 읽기 쉬운 스크롤을 허용한다.
- 공통 왼쪽 패널은 유지하고, 화면 제목·탐색·검색·필터·주요 동작의 위치와 라이트/다크 상태를 통일한다. 같은 수치와 설명을 의미 없이 반복하지 않는다.
- 기존 로그인, 권한, AIS, 계획 계산, 수기 원장, 엑셀, 3D 및 운전 모사 기능을 보존한다. 외형을 바꾸더라도 작동 여부를 따로 확인한다.
- 실제 관측·수기 입력·저장 계획·추정·모사를 출처와 시각으로 구분한다. 미수신은 0이 아니며 관측만으로 확정 시각이나 운전 상태를 만들지 않는다.
- ZGX의 실제 공용 자료를 테스트로 변경하지 않는다. 검증은 격리된 DB와 계정에서 한다.

## 현재 확인한 구조

`src/domain/navigation.ts`에는 운영 6개, 계획·분석 4개, 데이터 4개, 관리 2개 메뉴가 있다. 항차 화면 안에는 배선·화물·성상·선박 원장이 있고, 구매 검토는 시뮬레이션에서 열린다. 독립된 운전 모사 조작반도 있다.

새 화면이 없는 것은 아니다. `src/App.tsx`에서 접안·저탄·상탄의 새 화면과 기존 혼탄 분석, 기존 정지계획·시나리오·데이터 화면을 함께 연결하고 있어 화면별 구성과 입력 경로가 다르다. 원장과 혼탄 추천 관련 코드도 존재하지만, 모든 화면이 최신 공용 데이터를 같은 기준으로 표시하는지는 흐름별로 검증해야 한다. 코드 존재를 연동 완료로 간주하지 않는다.

## 메인: 발전·수급 전망 구성안

메인은 단순 현황 요약이 아니라 **발전 계획이 석탄 소비로 이어지고, 입하를 반영한 재고가 언제 어떻게 바뀌는지 판단하는 작업 화면**이다. 기존 운영 개요의 저장 계획 조회를 중심으로 재구성하고, 운영 현황은 공통 패널과 필요한 상세에서 연결한다. 기존 `#overview` 진입과 저장 계획 조회는 유지한다. 화면 명칭은 우선 ‘발전·수급 전망’으로 제안한다.

현재 저장 결과 계약에는 당진 1~10호기의 발전량·이용률·연료량, 일별/월별 계획, 저탄장군별 재고·입하·소비, 계획정지, 전국 수요와 석탄 발전 모델 결과가 있다. 이들은 동일한 단위나 범위가 아니다. 일부는 미보존일 수 있으며, 당진 계획과 전국 전망, MWh/MW, 실제 재고와 계획 시점의 전망을 각각 구분해 보여준다.

### 1920×1080 첫 화면 배치

```text
┌ 왼쪽 공통 패널 ┬ 발전·수급 전망   [저장 계획] [시작일] [7·30·60·90일] ┐
│ 출력·재고·접안 │ 기준시각 / 계획 출처 / 확인이 필요한 입력              │
│ 운영 메뉴       ├ 발전 계획       연료 사용        예상 최저 재고        │
│                 │ MWh · 기간 합계   t · 기간 합계    t · 날짜 / 미확정     │
│                 ├───────────────────────────┬──────────────────────────┤
│                 │ 수급 전망                 │ 확인할 변화               │
│                 │ 재고 추이와 기준선        │ 부족 우려·입하·정지 일정 │
│                 │ 선택한 시점의 입하·소비  │ 출처와 관련 화면 연결    │
│                 ├───────────────────────────┼──────────────────────────┤
│                 │ 호기별 발전·연료 계획     │ 저탄장별 재고·입하 요약   │
│                 └───────────────────────────┴──────────────────────────┘
└─────────────────┴──────────────────────────────────────────────────────┘
```

- 가운데 수급 전망을 가장 크게 배치한다. 기간별 재고 추이와 기준선을 중심으로 날짜를 선택하면 해당 날짜의 입하와 소비 및 관련 근거가 같이 바뀌도록 설계한다. 항차·재고·호기 상세를 열 수 있게 한다.
- 호기별 계획은 1~10호기의 발전·이용률 또는 연료량을 비교하고 계획정지를 함께 살펴보는 영역이다. 정지 일정은 미등록과 정지 없음이 다를 수 있다.
- 오른쪽은 차트를 반복하는 숫자 카드가 아니라 확인할 변화와 이유, 연결된 다음 작업을 보여준다. 부족 시점·임계선은 계산에 필요한 입력과 기준이 있을 때만 표시한다.
- 전국 전력수요·태양광·석탄발전 전망과 모델 근거, 월별 상세, 정지계획 및 계산 출처는 메인에서 접근 가능한 아래 상세나 별도 보기로 둔다. 당진 수급과 구별하면서 기존 정보는 유지한다.
- 비교·가정 변경은 통합 시뮬레이션에서 하고, 선택한 계획과 기간을 가능한 범위에서 이어받는다. 구매 검토는 그 결과에 연결한다. 이미 존재하는 기능과 새 계산이 필요한 부분을 구현 전 구분한다.
- 로딩, 저장 계획 없음, 기준재고 누락, 오래된 자료와 연결 오류를 구별한다. 초기 로딩은 스켈레톤으로, 확인 후 없는 값은 미확정으로 표시한다. 예시 수치를 실제 운영값으로 채우지 않는다.
- 좁은 화면에서는 전망 → 확인할 변화 → 호기·저탄장 상세 순으로 재배치하며, 1920×1080 기준 핵심을 한 화면에 담는다. 원문 수치와 출처는 상세에서 확인할 수 있어야 한다.

## 공통 데이터 흐름과 확인할 조건

1. 선박 관측과 사용자가 등록한 배선을 연결한다. AIS 접안은 추정으로 구분하고, 확인 가능한 이력 없이 도착 시각을 확정하지 않는다.
2. 계획 배선은 항차번호 없이 저장할 수 있다. 정식 번호는 연도·부두·일련번호 형식이며 충돌을 서버에서도 검증한다. 배선과 화물의 공통 정보는 재입력시키지 않는다.
3. 화물의 선적·하역·바이어 분석을 각각 보관한다. 혼탄 계산에는 하역 분석을 우선하고 없으면 선적 분석을 사용하며, 누락과 기준을 표시한다. NCV 기준은 확인 전 임의로 확정하거나 환산하지 않는다.
4. 입고는 실제 석탄이 들어온 날짜다. Pile과 물량은 우선 수기로 배분·정정하며 이력을 남긴다. 재고 전망에는 기준시각 이후 실제 입하만 더해 중복 집계하지 않는다.
5. 1저탄장 사용 범위는 사용자가 제한 해제를 알려준 상태다. 기존 화면이나 참고 데이터에 남은 제한 표시를 찾아 확인하고, 근거 없이 실제 운전 제한을 새로 만들지 않는다.
6. Pile별 공간과 사용기간, 실제 소비순서 등 입력이 없으면 구매 가능성과 추천을 확정하지 않는다. 설비 형상·상태·물량도 실제 연결과 시연을 분리한다.

## 순차 작업과 완료 기준

아래 각 묶음은 별도로 확인 가능한 결과물이다. 하나의 계획으로 순서대로 진행하되 화면만 일괄 교체하지 않고 실제 사용자 흐름 단위로 연결한다. 각 단계에서 현재 작업 내용을 보존하고 필요 시 별도 버전으로 남긴다.

1. **기준 정리와 화면 감사** — 기존 변경사항과 실행 구성을 보존하고 각 메뉴의 실제 입력·출력·데이터 출처·중복 기능을 목록화한다. 제한 해제와 실제 연결 상태 등 오래된 표시를 확인한다. 완료: 화면별 유지·이관·삭제 후보와 기능 손실 방지 목록이 나온다.
2. **공통 작업 틀** — 제목과 경로, 좌측 패널, 행동 버튼, 검색·필터, 표와 상세, 빈값·로딩·오류, 다크모드를 같은 규칙으로 정리한다. 완료: 주요 화면에 공통 규칙이 적용되고 기존 로그인과 탐색이 유지된다.
3. **발전·수급 전망 메인** — 저장 계획과 기준시각, 발전·연료·재고 전망을 위 구성에 맞게 재배치하고, 호기·저탄장·관련 항목으로 연결한다. 기존 전국 전망과 상세는 보존한다. 완료: 같은 계획·기간의 핵심 지표와 차트가 일치하고 출처, 결측, 당진/전국 범위가 분명하다.
4. **항차·화물과 데이터 입력** — 선박 추적에서 배선·화물·성상 등록, 검색과 엑셀 일괄 입력까지 정리한다. 계획번호 미정, 번호 충돌, 중복 입력 방지와 분석 우선순위를 확인한다. 완료: 한 번 입력한 정보가 관련 원장과 상세에서 이어지고 오류를 확인할 수 있다.
5. **접안·하역 → 저탄·재고** — 관심 선박과 부두별 접근 가능 경로, 입고, Pile 배분·정정과 현황을 연결한다. 실제 데이터, 추정, 모사와 기준시각을 명확히 한다. 완료: 한 화물의 이동과 재고 반영·정정 결과를 관련 화면에서 같은 기준으로 확인한다.
6. **상탄·혼탄 → 호기·연소** — 기존 3D와 분석을 하나의 작업 흐름으로 정돈하고 재고·대표 성상·혼탄 조건·호기 정보를 연결한다. 실제 설비 신호가 없으면 미연결로 둔다. 완료: 선택한 원탄의 근거와 사용 조건, 가능한 추천 및 누락 사유를 확인한다.
7. **시뮬레이션 → 구매 검토** — 기준과 대안을 비교하고 결과를 구매 검토에 넘긴다. 산지 리드타임·재고 부족·공간·저장기간을 계산에 실제로 쓸 수 있는지 단계적으로 확인한다. 완료: 조건, 출처 및 계산 가능한 범위가 유지되고 부족한 입력에 대한 결과는 확정하지 않는다.
8. **나머지 계획·분석·데이터·관리** — 정지계획, 계획·실적, 시나리오, 수급·모델·연결 화면을 정리하고 메인의 실제 데이터 연결을 보강한다. 완료: 모든 메뉴가 같은 탐색·상태 규칙을 쓰고 과거 화면으로 잘못 이동하지 않는다.
9. **전체 검증과 전달** — 격리 환경에서 항차 등록 → 입고·Pile 배분 → 성상·혼탄 → 전망·구매의 흐름과 권한, 엑셀, 모사 연결·단절을 검증한다. 1920×1080, 작은 화면, 라이트/다크와 키보드 조작을 확인한다. 완료: 실행한 테스트와 남은 미연결 항목을 구분해 보고한다. ZGX 배포는 코드 완성과 별도의 절차다.

각 단계는 구현 전에 해당 화면과 데이터 계약의 상세 작업으로 나눈다. `npm test`, `npm run build`, `npm run test:ui` 및 해당 흐름의 회귀 검증을 수행하며, 공통 UI·계약 변경은 저장소 규칙에 따라 검토한다.

## 진행 기록

- 입하 연계 확인: 격리된 원장과 화면에서 배선 입력 → 입고 → Pile 배분·정정 → 저탄 화면 수기 잔량 흐름을 검증했다. 도면상 정확한 위치가 없는 수기 잔량은 별도로 표시한다.
- 성상·수급 확인: 같은 격리 DB에서 하역 분석 우선, 혼탄 조건, 기준시각 이후 입고와 기준재고 재설정 시 중복 제외를 검증했다. 기준재고와 이후 입하 재고는 원탄별 소진이 확인되지 않아 혼탄 대상에서 동시에 선택하지 않는다.
- 구매 검토: 조회 시작일 발주 가정과 리드타임 이후 발전처 합계 기준으로 일말 전망에서 처음 공간이 확보되는 날짜를 표시한다. Pile 접근, 소진 순서와 저장기간 내 사용 여부는 확정하지 않는다.

- 메인 1차: 발전·연료 합계와 전망 재고, 날짜별 재고·입하·사용·발전계획, 계획정지와 호기별 계획을 배치했다. 선택한 날짜는 수급 원장 상세로, 선택한 계획은 시뮬레이션으로 이어진다. 일별 수치가 일부 빠진 합계는 미확정으로 둔다.
- 공통 표현: 운영 화면은 실제 관측·참고값·운전 시연의 차이를 업무 용어로 표시한다. 저탄 업무의 석탄 더미 명칭은 유지한다.
- 항차 원장: 검색어와 날짜·상태 조건으로 결과가 없는 경우를 기록 자체가 없는 상태와 구분하고, 조건 초기화를 제공한다. 검색어 앞뒤 공백은 무시한다.
- 항차·화물: 관심 선박과 MMSI가 일치하는 공용 배선 및 화물을 표시하고, 선택한 배선의 원장 상세로 연결한다. 복수 배선은 각각 표시하며, 중복 선박 식별자는 확인이 필요하다. 개인 항로 설정의 일정과 공용 원장을 구분한다.
- 남은 작업: 메인과 상세 원장의 연결을 포함한 항차·화물의 나머지 구조, 이후 접안·저탄·혼탄·계획 화면의 단계별 통합은 계속 진행한다. 전체 계획이 완료된 것은 아니다.
