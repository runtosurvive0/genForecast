# 공용 항차·화물 DB와 엑셀 교환 설계

작성일: 2026-11-06. 사용자 요청: 사람이 입력하는 항차 DB, 엑셀과 호환되는 헤더 및 관련 DB 구성.

## 구조와 선택

기존 개인 관심 선박 JSON 확장은 여러 담당자의 같은 항차 관리와 화물별 수정 이력에 부적합하다. 새 독립 서버를 만드는 대신 기존 ZGX Python/SQLite와 인증을 사용한다. 하나의 공용 업무 DB에 관계형 테이블을 추가한다. 현재 개인 관심 선박·AIS와 입하 원장은 보존한다.

- `voyage_registry_ships`: 선박코드(키), 선박명, MMSI, IMO, 선사, 선적국, 비고.
- `voyage_registry_voyages`: 항차번호(키), 선박코드(FK), 출항항, 주 도착항, 접안부두, 진행상태, 예정 출항/입항/접안/하역완료, 실제 출항/입항/접안/하역완료, 비고.
- `voyage_registry_cargo`: 화물번호(키), 항차번호(FK), 목적발전소코드, 공급사, 산지국가, 탄종, 계약번호, B/L번호, 예정물량(t), B/L물량(t), 열량(kcal/kg), 열량기준, 전수분/회분/황분(%), 회분·황분 분석기준, 비고.
- `voyage_registry_audit`: 변경자·시각·입력 경로·변경 전/후 값. 변경 이력 보존.
- `voyage_registry_meta`: 전체 원장 revision. 동시 수정과 엑셀 미리보기 이후 변경 충돌 방지.

MMSI/IMO는 선박 조회 연결값이며 항차의 식별자로 쓰지 않는다. 같은 배의 반복 항차와 한 항차의 여러 화물을 지원한다. 빈 숫자·날짜는 null이며 0으로 바꾸지 않는다. 날짜는 KST로 해석·저장·표시한다. 수정은 코드/번호를 기준으로 하며 누락된 행을 자동 삭제하지 않는다. 취소된 항차도 보존한다. 삭제 API는 이번 범위에 넣지 않는다.

## 엑셀

한 통합문서에 선박·항차·화물 3개 입력 시트, 작성안내와 코드표를 제공한다. 첫 행은 고정 한글 헤더, ID와 MMSI/IMO는 텍스트 형식, 날짜 헤더는 `(KST)`, 물량/탄질은 단위를 포함한다. 헤더 순서는 바뀌어도 이름으로 매핑한다. 미등록 값은 빈 셀, 0은 명시적 0이다. 수식 셀은 계산 결과를 추정하지 않고 오류로 안내한다.

필수: 선박의 선박코드/선박명, 항차의 항차번호/선박코드/진행상태, 화물의 화물번호/항차번호/목적발전소코드/탄종 및 예정물량 또는 B/L물량 중 하나. 열량을 입력하면 열량기준, 회분·황분을 입력하면 분석기준도 필수다. 서로 다른 기준을 임의 환산하지 않는다. 전수분은 AR 기준이다. 한 항차의 화물별 목적 발전소가 다를 수 있다.

업로드 → 서버에서 파일·헤더·행·FK·중복·시간 순서 검사 → 신규/수정/동일 건수와 행별 오류 미리보기 → 사용자가 반영. 오류가 있으면 전체 저장을 막고, 반영 시 동일한 검증과 revision 확인을 다시 수행한다. 엑셀 내보내기와 다시 가져오기는 값과 관계를 보존한다. 파일에 없는 기존 행은 유지한다. 최신 revision 없는 변경 파일은 미리보기 시점과 비교한 뒤 반영한다.

최대 4MB XLSX, 3개 시트 합계 5,000행, 압축 해제 크기 제한. 코드 중복, 존재하지 않는 참조, 음수 물량, 탄질 범위, 잘못된 날짜·수식·알 수 없는 헤더를 행과 열 이름으로 표시한다. 외부 링크와 매크로는 실행하지 않는다.

## 화면

항차·화물의 기존 지도 화면에서 `항차 DB`로 전환. 같은 로고·파란 운영 패널·테마를 유지한다. 선박/항차/화물 탭, 검색, 명확한 단위가 있는 표, 직접 등록/수정, 템플릿 다운로드, 가져오기, 내보내기, 변경 이력을 제공한다. 등록 폼은 공통/일정/화물 필드를 구분한다. 취소나 저장 실패는 원장을 바꾸지 않는다. 로딩·오류·빈 목록을 별도로 표시한다.

공용 DB의 항차는 개인 관심 항차 가정이나 AIS 실측값을 자동 덮어쓰지 않는다. AIS는 MMSI로 별도 관측을 조회하고 이 원장의 계획·실적 입력 출처는 `수기/엑셀`로 표시한다. 공용 항차 등록만으로 재고 입고를 발생시키지 않는다. 기존 입하 원장의 확정 하역 기능을 유지한다.

## 권한과 적용

사용자 확정: 승인된 팀원 모두 조회·입력·수정·엑셀 반영. 기존 인증·CSRF·계정 변경 검사를 사용한다. 다른 공용 입하·설정 API의 관리자 전용 정책은 유지한다. 실제 ZGX 자료에 테스트 쓰기를 하지 않는다. 격리 DB로 API/UI를 검증한다. 공용 사용은 서버 코드 업데이트가 필요하며 배포는 별도 작업이다.

## 검증

DB 재시작 후 보존, 다중 항차/화물, 참조·중복·범위·시각 검증, 원자적 롤백, 동시 수정 충돌, 감사 이력, 엑셀 템플릿/내보내기 왕복, 수식·과대 파일 거절, 로그인·권한·CSRF를 검증한다. UI는 수기 입력→수정→엑셀 미리보기→반영, 오류 보존, 테마·1920×1080/모바일을 확인한다. npm test/build/test:ui와 Python 단위 테스트를 실행한다.
