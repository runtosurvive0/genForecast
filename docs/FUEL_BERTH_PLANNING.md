# 부두 배정과 연료수급 전망

데이터/관리자 → **수급 배정·시뮬레이션**에서 항차 화물을 등록하고, 부두 추천을 확인한 뒤 관리자가 배정을 확정한다. 발전소 종합과 저탄장 현황은 같은 계산 ID·기준일·기간·전망 옵션을 사용한다. 저탄장의 처별 재고·하역선·컨베이어 수치는 DB 전망이며, Pile 위치·센서는 기존 모의 표본이다.

## 사용자 흐름

1. 완료된 MILP 결과와 조회 기준일을 선택한다. 처별 연료소모는 이 발전계획과 기존 열량곡선/HR·혼합 열량으로 계산한다.
2. 자기 선박추적 항차 중 당진행 항차를 불러오거나 화물량(t), 열량(kcal/kg), ETA(KST), 항차 키를 입력한다. 기본 등록은 선택한 계산에만 적용하는 가상 항차다. 운영 계획 등록은 별도 체크한다.
3. 추천은 ETA와 조회 기준시각 중 늦은 시각부터 빈 부두를 우선한다. 빈 부두끼리는 연결 처의 하역 시작일말 예상 재고일수가 낮은 순서다. 모두 점유 중이면 빠른 접안 가능시각을 우선한다. 자료가 없는 위험도는 미확정이며 체선 포함 가상 배정을 보류한다.
4. 관리자가 부두와 시작시각을 확인하여 확정한다. 충돌·하역량 등록·실제 접안·오래된 배정 버전은 서버에서 거절한다. 변경과 취소는 새 버전으로 남긴다. 취소는 예약만 해제하며 항차 화물은 보존한다.
5. **두 전망 계산·저장**으로 기본/체선 포함 결과를 동시에 저장하고 일별 결과를 비교한다. 기존 저장 결과는 당시 입력과 결과를 유지한다.

항차 키는 같은 업무 항차의 공통 계획과 가상 시나리오를 연결한다. 동일 키·동일 내용의 재전송은 중복 등록하지 않고, 같은 키의 다른 내용은 409를 반환한다. 같은 계산의 가상 항차가 공통 항차와 같은 키를 가지면 공통 항차를 대신하여 조회한다. `새 항차 입력` 버튼으로 새 키를 만든다.

## 계산과 상태

```text
처별 일말 저탄량 = 일초 저탄량 + 당일 하역 배분량 - 계획 연료소모 ± 처간 이탄
항내 확보량 = 처별 저탄량 합계 + 대기·하역 중 선박의 남은 화물
```

- `assigned`(기본): 확정 예약과 기존 하역 원장만 처별 입고에 반영한다. 미배정 화물은 처별 저탄량에 미리 더하지 않는다.
- `include_waiting`(체선 포함): 미배정 항차를 ETA 순으로 가상 접안·하역한다. 앞선 가상 배정과 확정 예약을 함께 점유로 취급한다. **가상 배정은 실제 예약·누적 하역 원장을 수정하지 않는다.**
- BD-1→1처(g14), BD-2→2처(g58), BD-3→3처(g910). 기본 능력은 부두당 7,000t/일, 마지막 날은 잔량까지만 반영한다. 기존 명시 하역율·중단·누적 실적을 보존한다.
- 하역된 물량은 저탄량에 늘고 선박 잔량에서는 줄어든다. 선박의 원래 화물을 다시 더하지 않는다. 음수 전망은 계획상 부족량이며 미등록 재고는 null이다.
- 현재 항내량은 입항 관측 또는 명시된 가상 항차로 계산한다. 운영 항차의 ETA가 지났지만 입항 관측이 없으면 현재 항내량은 미확정이다. 미래 전망은 등록 ETA에 입항한다는 가정이다.
- 미접안 관측은 과거 하역 계획에 따른 가상 소비를 막는다. 실제 접안·누적 하역이 예약보다 우선한다. 실제 접안선의 하역 완료가 확인되거나 예상 완료시각이 이미 지났어도 출항 관측이 없으면 부두를 빈 것으로 확정하지 않는다.
- 예상 접안·완료는 계획이고 실측이 아니다. 대기 시간 관측이 없으면 미확정이며 계약상 체선료를 계산하지 않는다.

## DB와 API

기존 `supply_vessels`, `supply_port_visits`, `supply_unload_points`, 기준재고·재고 lot·이탄·MILP 테이블을 재사용한다. 서버는 다음 4개 테이블과 항차 키 열/고유 인덱스를 필요 시 생성한다. 초기 DB 사본은 바꾸지 않는다.

| 테이블 | 저장 내용 |
|---|---|
| `supply_berths` | 3개 부두, 연결 처, 하역능력, 사용 여부 |
| `supply_berth_assignments` | 항차별 배정 버전, 부두, 시작·종료, 예약/취소, 작성자·기록시각 |
| `supply_simulation_runs` | 비교 실행 ID, 입력 스냅샷, 두 옵션 요약, 작성자·기록시각 |
| `supply_simulation_daily` | 비교 실행 ID·KST 날짜별 두 옵션 결과 |

입력 스냅샷은 원장·당시 부두 조건/예약·MILP 시간계획·호기 용량/열량곡선·기준 발열량·조회기간을 보존한다. `midterm.berth_planning.replay(snapshot, mode)`는 이후 변경된 DB를 읽지 않고 재계산한다.

| API | 용도 |
|---|---|
| `POST /api/supply/shipments` | 미배정 화물 등록. `run_id=null`은 공통 계획, 지정 시 가상 계획 |
| `GET /api/supply/berths` | 부두와 항차별 최신 배정 |
| `PUT /api/supply/berths/{berth_id}` | 하역능력·사용 여부. 진행·예약 중 조건 변경 제한 |
| `GET /api/supply/berth-recommendations?run_id=…&start=YYYY-MM-DD&horizon=30&vessel_id=…` | 3개 부두 후보와 배정 버전 |
| `POST /api/supply/berth-assignments` | 부두 확정·변경·취소. `expected_version` 필수 |
| `POST /api/supply/simulations` | 동일 입력의 두 전망 계산·저장 |
| `GET /api/supply/simulations` | 최근 저장 실행 50개 |
| `GET /api/supply/simulations/{id}` | 저장된 일별 비교 결과 |

`/api/supply/dashboard`와 `/api/planning/runs/{run_id}/snapshot`에 `inventory_mode=assigned|include_waiting`을 전달한다. 응답에는 항내 잔량·확보량, 가상 배정, 점유 일정, 일별 부족량이 포함된다. 구버전 서버가 체선 옵션을 지원하지 않으면 화면에 오류를 표시한다.

공통 원장 등록·배정·부두 조건 변경은 관리자, 조회·비교 계산 저장은 승인된 회원 권한이다. 쓰기는 기존 세션·CSRF 검사를 따른다. 예약 충돌과 버전 검증은 SQLite 쓰기 트랜잭션에서 최신 원장으로 다시 확인한다.

## 확인 환경과 남은 연계

로컬 개발은 `MIDTERM_API_TARGET=http://127.0.0.1:8093`과 별도 `MIDTERM_PLANNING_DB`로 수행한다. 팀 공용 ZGX와 실제 운영 자료에 테스트 화물을 등록하지 않는다. [초기 DB 등록](../backend/seeds/README.md)으로 2027 가상 결과와 64만 톤을 준비할 수 있다. 코드 병합만으로 공용 서버 배포·자료 등록이 실행되지는 않는다.

이번 기능은 **선박추적 항차의 명시적 불러오기와 계획 하역**을 제공한다. AIS 위치로 입항을 자동 판정하는 수집기는 아직 연결하지 않았다. 실제 입항·접안·출항은 기존 `POST /api/supply/port-visits` 관측 계약으로 등록해야 한다. 내부망 발전 실적의 자동 수집, 혼탄 품질 제약을 포함한 최적 부두 배정, 실제 Pile별 입출고는 후속 단계다. 현재 추천은 재고일수와 점유 시간의 순차 규칙을 사용한다.
